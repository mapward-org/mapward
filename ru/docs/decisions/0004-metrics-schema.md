# Схема метрики

Конфиг метрики это пайплайн collectors, transforms, display

Вместо создания кучи кастомных типов метрик в ядре, мы задаём базовые механизмы, которые уже будут использоваться для создания конкретных метрик

Вот тип `config.json` метрики

```ts
type Metric = {
  label?: string,
  extends?: string, // mapward:// адрес, см. решение 0005
                    // путь ведёт к директории с config.json, внутри _metrics лежать не обязана
  refresh?: "manual" | "on-display" | `interval:${string}` // default manual

  // Если передан коллекторы пишут в collect.json иначе данные передаются напрямую в transform
  collectorsCache?: boolean 
  collectors?: MetricCollect[],

  // Если передан трансформы пишут в transform.json иначе данные передаются напрямую в display
  transformsCache?: boolean 
  transforms?: MetricTransform[],

  display?: MetricDisplay,
}
```
Всё опциональное, так как любое поле может быть наследовано от родительского объекта или родительской метрики
Ui должен не ломаться но показывать `unknown`

Как получаем конкретную метрику  

Сначала резолвятся extends внутри метрики, а потом extends метрик объектов (рекурсивно, ошибка при циклах)

`{...{...parent.metric.extends, ...parent.metric}, ...{...metric.extends, ...metric}}`

### **label**  просто подпись метрики

нужна для отображения. Опциональна

### **refresh** - режим работы метрики
- "manual": Весь пайплайн сбора метрики запускается вручную. 
- "on-display": Пайплайн сбора метрики запускается в момент отображения метрики (удобно для быстрых метрик что бы не кэшировать в файлах). Пока данных нет, показывается лоадер
- "interval:${string}" - Пайплайн запускается с интервалом в ms указанном после :


### **display**

Определяет то как метрика будет отображаться. 
У каждого типа дисплея есть форма данных которую он принимает.

```ts
type MetricDisplay =
  | { kind: "text" }   // { text: string }
  | { kind: "link" }   // { label?: string, link?: string }
  | { kind: "status" } // { ok: boolean, summary?: string }
  | { kind: "list" }   // { items: ListNode[] }
  | { kind: "tree" }   // { children: TreeNode[] }
  | { kind: "map" }    // { nodes: MapNode[], relations: MapRelation[] }

type ListNode = {
  label?: string,
  link?: string,
}

type TreeNode = {
  label?: string,
  link?: string,
  children?: TreeNode[],
}

type MapNode = {
  label?: string,
  link?: string,
}

type MapRelation = {
  label?: string,
  link?: string,   // сама связь, если в неё можно провалиться
  from?: string,   // mapward:// адреса концов
  to?: string,
}
```

`link` - адрес по решению [0005](0005-addressing.md). По схеме понятно, как резолвить:
`mapward://` ведёт на объект карты, `https://` наружу, всё остальное файл в проекте —
рендерер превратит его в ссылку в зависимости от окружения

Если `link` ведёт на объект карты, отображение формируется на основе этого объекта,
а `label` игнорируется

Тип карты сохраняет в файле "map-state.json" координаты элементов и модификаторы линий (точки через которые они проходят)

`updatedAt` нужен что бы показывать метрики собранные давно. Его записывает сам рантайм при записи `collect.json` или `transform.json`, поэтому в формах данных его нет — он лежит уровнем выше, рядом с данными

```json
{ "updatedAt": "2026-08-28T04:10:00Z", "data": { "ok": true, "summary": "12 passed" } }
```

Если `updatedAt` нет (например у `static`), считаем метрику всегда фреш

Дисплей может брать данные из 3х мест 

`in memory state` - У каждой метрики есть in-memory state который заполняется после вызова collect transform пайплайна
`transform.json` - Кэш вызова трансформа
`collect.json` - Кэш  вызова коллекта

Приоритет сначала in memory потом transform если его нет collect
Если содержимое не соответствует типу данных дисплея. Карта не падает, пытаемся показать что можем и пишем ошибку

### **collectors**

Коллектор используется для сбора информации с любых источников и передачи их в файл или трансформу или дисплею напрямую

Коллект запускается в зависимости от "refresh"

Если несколько коллекторов, им нужен name, что бы результаты записать в общий объект.

Любая строка конфига может содержать подстановку, см. решение [0006](0006-substitution.md)

```ts
type BaseCollect = {
  kind: string
  name?: string // Под этим именем результат ляжет в общий объект.
                // Если коллектор один, имя не нужно — он и есть результат
}

type MetricCollect = BaseCollect & (
  | { kind: "static", value: unknown }
  | { kind: "script", run: string }
  | { kind: "prompt", prompt: string }
  | { kind: "read-dir", basePath: string, include?: string[], exclude?: string[] } // в include, exclude глобы
  | { kind: "object-children-map", relations?: string, nodes?: string }
)

```


**static** - Просто значение которое сразу передаётся в display или transform удобно для тестов и визуальных штук
**script** - Запускает скрипт текущей оболочки. cwd - корень карты!
Важно: скрипт запускается с переменными окружения содержащими информацию об объекте из `_index.json`

MAPWARD_OBJECT_PATH - относительный путь до объекта от корня карты
MAPWARD_MAP_PATH - абсолютный путь до корня карты
MAPWARD_OBJECT_NAME - имя объекта
MAPWARD_OBJECT - json со всем содержимым `_index.json`

**prompt** - медленный но простой вариант собрать метрику откуда угодно. По умолчанию запускается в headless режиме клода, команда агента настраивается в конфиге карты. В базовый промпт так же прокинута информация об объекте

**read-dir** - кастомный коллект, который собирает информацию с директории. basePath это файловый путь: относительный резолвится от cwd, надёжнее указывать через подстановку [0006](0006-substitution.md): `${{ mapward://#props.basePath }}`. Результат удобно передавать в tree дисплей

Формат вывода
```ts
type FileNode = {
  isDir?: boolean
  path: string 
  name: string

  // шейп удобный для tree дисплея
  label: string // name
  children: FileNode[]
}

type ReadDirRes = {
  children: FileNode[]
} 

```

**object-children-map** - читает детей текущего объекта и выводит конфиг в форме удобной для `map` дисплея
(Для релейшенов, у объектов в пропсах должно быть from to — mapward:// адреса объектов карты)

(relations, nodes) - по умолчанию все у кого есть (from,to) релейшены остальное ноды. Если хочется только часть показывать - то можно указать глоб относительно объекта

### **transforms**

Коллектор отдаёт то, что есть на источнике. Дисплей ждёт свою форму данных.
Трансформ приводит одно к другому.

Трансформ не обязателен. Если коллектор уже отдал нужную форму (`static` руками,
`prompt` попросили писать сразу в нужном виде) — пайплайн идёт мимо трансформов.

```ts
type MetricTransform =
  | { kind: "prompt", prompt?: string } // Без текста — цель берётся из формы дисплея
  | { kind: "script", run: string }     // Внешний скрипт, вход в stdin, выход из stdout
```

Трансформы идут по порядку. Выход одного — вход следующего. Первый получает
объект коллекторов и разбирает его по именам.

**prompt** - когда формат вывода плавает. Парсить регуляркой вывод тестраннера
хрупко, он меняется с версией. Промпт переживает.
Текст промпта чаще всего не нужен: форму данных дисплей знает сам, она уезжает
в промпт вместе с сырыми данными.

**script**  - когда формат стабильный. Работает мгновенно и бесплатно,
в отличие от промпта.

(В скрипт попадают env ровно такие же как в коллект)


Если трансформ упал, метрика не падает. Показываем прошлое значение и пишем ошибку.
