# Бизнес-требования

## Продукт

Mapward — инструмент контролируемой AI-разработки.

При работе с AI самое сложное — не потерять контроль над происходящим, а попытки контроль
удержать замедляют работу в разы. Человек становится руководителем, а не исполнителем, и
получает дилемму делегирования: полный контроль нейтрализует выигрыш, отсутствие контроля
даёт непредсказуемый результат.

Разрешается она так:

- важное контролирует человек;
- неважное делегируется AI;
- контроль неважного строится через измеримость важного.

Пока кодстайл не влияет на UX — это дело AI. Важное — связи, public api, тест-кейсы,
бизнес-требования — человек должен видеть и мерить.

Отсюда четыре требования к инструменту:

1. **Фильтровать важное** — собирать метрики и показывать их так, чтобы решение принималось
   глазами.
2. **Отделять человеческое от машинного** — то, что человек написал и решил, не смешивается
   с AI-генерацией.
3. **Настраиваться под уникальное важное проекта** — набор метрик не зашит в инструмент.
4. **Давать AI реализовывать неважное по директивам**, оставляя человеку метрики.

### Почему не хватает редактора

Классическое дерево файлов удобно для ручного письма кода: это масштаб подробностей.
Метрики важного живут выше — на архитектурном уровне, и в дереве файлов их не видно.

Поэтому mapward **конкурирует с файловой структурой за точку входа в проект**: файлы это
подробности, к которым спускаются при отладке, а не то, с чего начинают. Отсюда и форма —
изначально сайдбар, на месте привычного дерева.

### Почему не плоский список

Даже на архитектурном уровне объём информации велик, а одновременно человек удерживает мало
объектов. Зато он хорошо строит глубокие сети абстракций. Поэтому представление
иерархическое и графовое: на каждом уровне своя информация и свои решения, за подробностями
проваливаются внутрь.

### Оценку даёт человек

Метрики — не только то, что сводится к «зелено/красно», как тесты и деплой. Архитектуру
связей и public api автоматически не оценить. Карта их выводит; хорошо это или плохо —
решает человек.

## Сценарии

### Открыть карту

При установке расширения в activity bar появляется иконка mapward — самый левый таб.

По клику на неё расширение ищет карты: от каждой папки воркспейса вверх, дубли по пути
карты отбрасываются.

- одна карта — в сайдбаре открывается её корневой объект;
- несколько — аккордеон, секция на карту. Секции разворачиваются и сворачиваются, как
  корни воркспейса в проводнике;
- папка открыта, конфига в ней нет — кнопка создать `mapward.json`;
- папка не открыта вообще — кнопка найти: диалог выбора папки, дальше редактор открывает
  её как воркспейс.

### Объект

Объект в сайдбаре состоит из:

1. **Хлебные крошки** по объектам, с навигацией и кнопкой «назад».
2. **Название** в форме «название прототипа: название объекта» — «Пакет: core». Если
   прототипа нет, выводится только название объекта.
3. **Терминалы.** Если терминалов нет — создаётся новый claude-терминал в корне проекта
   (`baseUrl`) с базовым промптом, указывающим, с каким объектом работаем. Если терминал
   есть — открывается выпадающий список: кнопка создать новый и крестик, закрывающий
   терминал. Имя у терминала по дате-времени либо по директиве.
   Терминал без директивы — просто разговор об объекте; базовый промпт советует правки
   делать через директивы.
4. **Экшоны.** Список экшонов, клик по каждому открывает его файл.
5. **Директивы.** Список со статусами, отсортированный по дате в имени файла, от новых к
   старым. Статус директивы: новая, изменилась, выполнена. Клик по директиве открывает её
   файл, рядом три кнопки — валидация, тестовый запуск, запуск.
   Кнопки создают терминал с клодом и нужным промптом. По умолчанию на директиву
   используется один терминал; по правой кнопке можно вызвать в новом терминале или в
   другом существующем.
6. **Создать директиву.**
7. **Открыть объект как таб.**
8. **Сетка метрик**, адаптируется под ширину сайдбара на основе раскладки из конфига.

Если в метрике есть ссылка на дочерний объект, он открывается в сайдбаре; через выпадающее
меню можно открыть в табе.

### Метрики

Каждый тип `display` — свой компонент со своими пропсами. Если данные пришли не в той форме,
компонент показывает ошибку валидации.

Коллекторы запускаются в зависимости от настройки: при рендере объекта либо вручную.
Интервальные тикают, пока объект отрисован.

При наведении на label появляются две кнопки:

- **обновить** — есть у каждой метрики, включая запускаемые автоматически;
- **скрыть** — тогглер, прячет содержимое, label остаётся с кнопкой открыть. Удобно для
  громоздких карт. Скрытие запоминается в `workspaceState` расширения, то есть локально у
  человека, а не в репозитории.

Если у метрики есть `updatedAt`, рядом с label мелко показывается время с последнего
обновления.

После запуска коллектора рядом с label появляется лоадер; при наведении на него — крестик,
прерывающий операцию. По завершении вместо лоадера точка: зелёная при успехе, красная при
неудаче. Прошлые данные при неудаче не затираются.

Прогон пишет логи в `collect.logs.json`, трансформы — в свой файл. Клик по точке открывает
логи. Если сломался трансформ, точек несколько — на сбор и на преобразование, и по клику
открывается лог того шага, который упал.

Успешность прогона записывается в `collect.json` рядом с `updatedAt`.

Пока данных нет — не показываем ничего, только лоадер рядом с label. В том числе пока
читаются данные из кэша.

## Уведомления

Сессии клода могут уведомить пользователя — когда задают вопрос и когда заканчивают работу.
Клик по уведомлению открывает тот терминал, из которого оно пришло.

## Вотчеры

Карту часто правят руками и агентами — не только через интерфейс. Поэтому состояния карты,
метрик и директив отслеживаются на файловой системе, насколько это возможно, и изменения
подхватываются без перезапуска.
