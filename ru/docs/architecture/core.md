# core

Связка: то, что двум сторонам нужно понимать одинаково. Границы пакета — решение
[0014](../decisions/0014-client-server.md), слои — [0015](../decisions/0015-package-layout.md).

`core` начинался как «модель карты, общая у сервера и клиента», пока клиент сам собирал карту из
файлов. Теперь карту собирает только сервер, а клиент получает объект по мосту — и сборка ушла к
серверу (`abstract-server`, фича `map`). Здесь осталось то, без чего стороны не договорятся.

## Структура

```
src/
  contracts/     контракты моста и протокол; типы того, что по ним едет (Run…, Turn…,
                 Capabilities, ComponentBuild)
  lib/bridge/    клиент и сервер моста поверх контракта
  model/
    model.ts     объект карты как он едет по мосту (MapObject, MapMetric, MapAction, MapFile,
                 MapStage, ConfigLayer), выбор вкладки, поиск в дереве объектов
    configs.ts   конфиги `_index.json`, метрики и экшона — типами, без схем
    address.ts   адреса `mapward://` и куда ведёт ссылка
    folders.ts   имена служебных файлов и папок объекта, хозяин метрики и экшона по адресу
    inputs.ts    форма экшона и вопрос подтверждения
    git.ts       буква git на узле дерева
  index.ts       точка входа в пакет
```

## Кто с кем связан

- **сервер ↔ клиент и хост** — контракты моста, объект карты, прогоны, ходы, возможности хоста,
  собранный компонент (`ComponentBuild`);
- **платформа ↔ плагин** — `@mapward/plugin` встраивает `core` в свою сборку: объект в `ctx`,
  сообщения прогона (`runMessage`), операции и ответ правки карты (`MapEditOp`, `MapEditResult`
  в `contracts/edit.ts` — их же берут мост `editMap` и MCP `edit_map`);
- **сервер ↔ клиент одним ответом** — что считают обе стороны и где разойтись нельзя: форма экшона
  и вопрос подтверждения (`actionForm`, `confirmQuestion`, `complete`) — клиент решает, открыть
  ли форму, сервер — запустить ли, и MCP показывает агенту тот же вопрос; выбор вкладки
  (`pickGroup`, `groupMetrics`, `previewGroup`) — экран и MCP показывают одну вкладку;
- **плагин `files` ↔ клиент** — буква git (`GitLetter`): плагин метит узлы, клиент рисует.

Типы конфигов — TS-типы. Схемы typebox, которыми проверяется файл на диске, живут у сервера рядом
со сборкой (`features/map/domain/schema.ts`); что схема и тип не разошлись, проверяет компилятор
(`schema.test.ts` там же). Контракты моста — на typebox: параметры, пришедшие из вебвью, мост
проверяет схемой.

Данные кирпичей (пункт списка, узел дерева, `ActionRef`) описаны у самих кирпичей — в
`bricks/types.ts` встроенного плагина `views`; в `core` их нет. Клиенту из них нужен только
`ActionRef` — им называет экшон `useAction`; он лежит в `kernel/` клиента.

## Что сюда попадает

Не всё общее, а то, что нужно двум сторонам одинаково: у каждого модуля есть потребитель кроме
сервера — клиент, расширение, cli, `@mapward/plugin`, `@mapward/component` или встроенный плагин.
Нужное одному серверу — у сервера, даже если оно чистое и «могло бы пригодиться»: сборка объекта,
наследование, мердж, подстановки, схемы файлов, живая модель, frontmatter. Это сторожит
`tests/core-is-a-link.test.ts`; модуль без такого потребителя записывается там исключением с
причиной.

## Правила

`core` не зависит ни от кого. Ни от платформы, ни от пакетов, ни тем более от приложений —
это проверяет `tests/platform-independence.test.ts` и тест направления зависимостей.
