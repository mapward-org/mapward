# Проверка директивы `add-metric-to-interface-and-mcp`, объект `mapward://`

## Чем пользовался

- `read_docs { mcp }` и `{ directives }` — до всего остального. Раздел `mcp` окупился сразу:
  из него взял приём «обзор без метрик, потом метрики поимённо», и он же уберёг от вызова
  по всей карте со значениями.
- `read_object { depth: 2, metrics: [], fields: [...] }` — обзор. Первый заход сделал без
  `fields`, ответ ушёл в файл на 55 КБ; со списком полей уложился в один экран. То есть
  `metrics: []` от раздувания не спасает — раздувает раскладка и конфиги, и лечится это
  проекцией.
- `read_object { metrics: ["decisions", "decisions-drift"], refresh: "on-display" }` — список
  решений одним вызовом, с путями. Дальше `requirements-todo` и `requirements-links`.
- `read_index { file }` — текст директивы и текст экшона `add-requirement.md` с прототипа.
  Экшон оказался главной находкой проверки: правило «раздел по тому, что требование обещает
  наружу» прямо противоречит шапке директивы, и по файловой системе его было бы не найти.
- `run_directive` / `finish_directive`.
- Остальное — обычный `grep` по путям из `props.codePath` и из ссылок метрик.

## Что не получилось

- **Текст этапа воркфлоу через MCP не достаётся.** `read_index { file }` ходит только по
  директивам и экшонам; у этапа в `read_object.workflow` есть `path`, но читается он с диска.
  Промпт своего этапа приезжает с `run_directive`, а вот заглянуть в соседний — «что спросит
  „Реализация“, если я тут недоспрошу» — можно только файлом. Это уже записано в память карты,
  подтверждаю ещё раз.
- **Конфиг метрики без мерджа не посмотреть** — ровно то, о чём директива. Проверяя её же
  утверждение про `_metrics` и `findObject`, пошёл в исходники ядра; вызовом это не
  проверяется никак.
- **`decisions` отдаёт дерево имён файлов, а не решений.** Чтобы понять, про что `0016`, нужно
  открыть файл: в метрике только `0016-agent-context.md`. Для проверки «нет ли противоречий с
  решениями» это главный вопрос, и метрика на него не отвечает — отвечает `decisions-drift`,
  но только по уже найденным расхождениям с требованиями.

## Как было бы удобнее

- `read_index` по адресу метрики (`mapward://.../_metrics/files`) закрыл бы половину похода
  в исходники: `findMetric` в ядре уже есть, и `run_metric` этим адресом пользуется.
- Симметрично `file` не хватает доступа к телу этапа — `read_index { stage: "Реализация" }`
  или просто отдавать текст в `workflow`. Проверка по определению смотрит вперёд, на этап,
  который пойдёт по этому телу.
- Полезным оказался порядок «сначала `read_docs`, потом карта, и только потом `grep`». Ни одна
  из восьми находок не пришла из сканирования репозитория: пять из карты и экшона, три — из
  точечного `grep` по путям, которые карта назвала.
