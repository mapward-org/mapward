# Отзыв по директиве анализ-mcp, mapward:// — вся сессия

Брейншторм (5 кругов), План (6), Реализация, Тестирование.

## Что помогло

- `read_index { file, tail }` вместе с `bytes` и `lines` — на каждом круге хватало хвоста в 4–8 строк.
- `read_object { group, refresh: "on-display", fields: ["metrics.key", "metrics.value.ok"] }` —
  здоровье вкладки целиком за один дешёвый вызов, новая метрика сразу видна.
- На Тестировании вживую сработало то, что сделала директива: `build` в ответе, `known` →
  `unchanged: true`, отказ на `deepth`.

## Где ошибся или потратил лишнее

- Весь материал директивы (181 отзыв, 809 КБ) лежит мимо карты. Читали его четыре субагента
  с диска, кластеры я складывал руками.
- До перезагрузки окна живой сервер был старым. `run_action` и `read_run` уже лежали в
  исходниках, а в MCP их не было, и сказать об этом серверу было нечем. Теперь это поле `build`.
- Реплики я дописывал руками: `>>`, Edit, проверка конца файла через `od -c`. Ответ автора
  дважды кончался без перевода строки.
- Промпт этапа приходил полностью на всех одиннадцати кругах — около 55 КБ повторов.
- Номер решения: `0037` и `0038` оказались заняты, `ls` показал не сразу — смотрел не ту выборку.
- Обратный индекс метрики `links` проекцией не достать: ключи-пути содержат точки.

## Что сделало бы дешевле

- Метрика по `mcp-reviews` с кластерами просьб — такой разбор стал бы одним вызовом.
- `fields` с экранированием точки в ключе, или отбор по ключу словаря.
