# 2026-09-20 04:35 — Mapward (ru), этап «Тестирование» директивы «create-package-action»

## Чем пользовался

- `read_docs { section: "mcp" }`, потом `{ section: "directives" }` и `{ section: "addressing" }`.
  Первые два — как велит промпт, третий — когда искал, как адресуется метрика.
- `read_object` обзором. Как и в прошлый прогон, первый вызов без `fields` дал 55 КБ и уехал
  в файл; второй, с `{ depth: 2, metrics: [], fields: [...] }`, дал нужное.
- `read_object { address: "mapward://prototypes/package", fields: ["actions", "directives", "layout"] }` —
  это и был главный вызов проверки: директива требовала превратить директиву в экшон, и
  «`create-package.md` теперь в `actions`, а `directives.total` — ноль» видно одним ответом,
  без обхода папок.
- `read_index { file: "2026-09-19-1302-create-package-action.md" }` и то же по
  `create-package.md` у прототипа — текст директивы и текст получившегося экшона из карты.
  Для экшона это существеннее, чем для директивы: он лежит у прототипа, и путь к нему я бы
  склеивал руками.
- `read_object { fields: ["metrics.key", "metrics.owner"] }` по всей карте с `depth: 2`.
  Вопрос директивы «метрика заведена на своём объекте или приехала от прототипа» — это ровно
  `metrics.owner`, и проверяется он одним вызовом на всю карту. Без `owner` эффективный
  список у наследника и у своего объекта одинаковый и об этом молчит — тут поле отработало.
- `read_object { metrics: ["tests"], fields: [..., "metrics.config"] }` — увидеть подставленную
  команду. В файле прототипа написано `pnpm vitest run ${{ ... }}`, а нужно было убедиться, что
  на `core` это разворачивается в `pnpm vitest run packages/core`, а не в старый `--project`.
- `run_metric` по четырём пакетам — единственный способ узнать, что метрика «Тесты» действительно
  починена.

## Что не получилось

- **Адрес метрики нигде в `read_docs` не показан.** Схема `run_metric` говорит «`mapward://`
  адрес метрики», раздел `addressing` перечисляет формы адресов и метрик среди них нет. Я
  угадал `mapward://packages/core#metrics.tests`, получил «не найдена», полез в исходники
  (`findMetricOwner`) и нашёл настоящую форму только в ответе `read_object` — там есть
  `metrics.address`. Само поле `address` при этом не упомянуто и в списке «что ещё есть у
  метрики» в разделе `mcp`: там `key`, `config`, `owner`, `logs`. Смешно, что в help'е CLI
  форма написана прямым текстом: «Адрес метрики — `mapward://<объект>/_metrics/<имя>`».
  Одна строка в `addressing` сняла бы весь этот круг.
- **Кэш метрики врёт, а файл кэша врёт увереннее.** `prototypes/package/_metrics/tests/collect.logs.json`
  до сих пор хранит падение старой команды `--project @mapward/core` — то есть ровно ту
  картину, которую директива требовала починить. Если бы я проверял «починена ли метрика»
  чтением файлов, я бы написал «не починена». Правду дал только `run_metric`. Для этапа
  «Тестирование» это общее правило: у ручной метрики читать кэш нельзя, её надо звать.
- **Карта не связывает директиву с изменением.** Проверять «сделано ли» пришлось через
  `git show --stat` по коммиту, найденному по названию. В `_directives.state` лежит побайтная
  копия текста, но не то, что после прогона поменялось. Диффом это смотрит человек, а агенту,
  пришедшему на этап «Тестирование» в новой сессии, приходится угадывать коммит по формулировке.
- **Ничто не проверяет, что имя в раскладке метрик существует.** Директива убрала метрику
  `docs` у прототипа `Пакет`, а `details-metrics-layout` до сих пор перечисляет `docs` в первой
  строке. Ни `read_object`, ни какая-либо метрика об этом не говорят — область просто пустая.
  Это дешёвая проверка формы, как раз для `check`.
- **`pnpm check` из корневого `package.json` мёртв.** `node apps/cli/dist/cli.mjs check map`
  печатает help и падает с кодом 1: команды `check` у CLI больше нет. Не по этой директиве, но
  прогон «что проверяется прогоном» об это спотыкается.

## Как было бы удобнее

Для этапа «Тестирование» не хватает одного: ответа на вопрос «что изменилось с прошлого
прогона». Всё остальное MCP отдаёт лучше, чем файловая система, — а вот сопоставление текста
директивы с состоянием проекта каждый раз собирается руками из `read_object`, `git` и запусков.
