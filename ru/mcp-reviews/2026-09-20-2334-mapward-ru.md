# Отзыв: этап «Реализация» по директиве про git-статус

## Чем пользовался

- `run_directive` и `read_index { file, tail }` — промпт этапа и свежие ответы автора на два
  вопроса второго круга. Хвоста в 30 строк хватило, файл целиком поднимать не пришлось.
- Обзорный `read_object { depth: 3, fields: ["address", "metrics.key", "metrics.owner"] }` —
  этим я отобрал двадцать метрик, в которые надо было проставить шаг. Перечень метрик приходит
  без сбора, поэтому глубина ничего не стоила: один вызов вместо обхода `_metrics` по папкам.
- Метрика `files` на `abstract-server` — карта путей для правок. Дальше `grep` по указанным
  местам, как велит промпт.
- `read_docs { section: "metrics" }` — раздел про пайплайн; по нему сверял, куда встаёт третий
  вид шага и чем он отличается по свежести.

## Что не получилось

**Конфиги метрик пришлось править мимо карты.** Ответ автора «проставь везде» означает двадцать
файлов `config.json`, и карта их отдаёт только на чтение — `read_index` по адресу метрики. Писать
пришлось скриптом по путям с диска, а путь метрики в ответе есть (`configPath`), но у
унаследованной он ведёт к прототипу, и чтобы не проставить шаг двадцать раз в один и тот же файл,
я сначала отобрал метрики с `owner` и выбросил их. Это ровно та работа, которую карта уже умеет,
но наружу не отдаёт: «покажи метрики, чей конфиг лежит здесь, а не у прототипа».

**Проверить сделанное картой нельзя.** Живой MCP обслуживает `dist` открытого расширения, и
после правки сервера он показывает прежнее поведение. Прогон метрики ушёл в cli
(`node apps/cli/dist/cli.mjs metric <адрес>`), а `run_metric` через MCP на этом этапе бесполезен
— он бы соврал зелёным на старом коде. Для этапа Реализации это главное неудобство: инструмент,
который правишь, во время правки показывает вчерашнюю версию себя.

Первый прогон после правки я к тому же прочитал неверно: `metric` печатает дерево целиком, первые
сорок строк оказались неизменёнными файлами, и я успел решить, что шаг не сработал. Помог
`grep -B3 '"git"'` по выводу. Ответ, в котором значение метрики — двести узлов, на вопрос
«появилась ли пометка» не отвечает, сколько в него ни смотри.

## Как было бы удобнее

Отбор по содержимому значения — `read_object`, который отдаёт только узлы, у которых есть
названное поле. Сейчас `fields` режет по ключам объекта карты, а не внутри `metrics.value`,
и вопрос «где в этом дереве пометки» решается grep-ом по json. Для проверки своей же работы
это самый частый вопрос.

Ещё пригодился бы признак «метрика заведена здесь, а не унаследована» в отборе, а не только
в ответе: `owner` приходит полем, и отфильтровать по нему можно лишь после того, как ответ уже
собран со всеми метриками всех объектов.
