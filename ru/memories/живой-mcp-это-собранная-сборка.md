---
description: правку в packages/*/src живой MCP не видит — он обслуживает dist открытого расширения
---

MCP-сервер, через который агент читает карту, поднимает открытое в редакторе расширение — то
есть исполняется `dist`, собранный на момент его запуска. Поправил `packages/*/src` — вызовы
`read_object` и `run_directive` по-прежнему отвечают по-старому, даже после `turbo run build`:
нужен перезапуск расширения.

Хуже того, **неизвестный параметр старая сборка молча проглатывает**: зовёшь
`read_index { file, tail: 12 }`, получаешь успешный ответ — и в нём весь файл, потому что
ветки `tail` в `dist` ещё нет. Ответ правильный по форме и не тот, который просили; отличить
его от настоящего можно только по содержимому.

Поэтому изменение в чтении карты проверяется не вызовом MCP, а прямым прогоном модели карты
над настоящей папкой — `new MapModel(files, files, timers, clock).current(ref)` скриптом на
`packages/abstract-server/dist/index.mjs` или временным vitest-тестом, с портом `files` на
`node:fs` (с 2026-09-23 функции `readMap` нет — решение 0041). Занимает секунду и показывает то же самое. Второй способ, если новое
сидит в самом MCP, а не в чтении карты: поднять свой сервер по stdio —
`node apps/cli/dist/cli.mjs mcp` — и разговаривать с ним json-строками в `stdin`. Это свежая
сборка, и она независима от открытого расширения (проверено 2026-09-20 на `read_index { stage }`
и `run_metric { wait: false }`).

То же самое с документацией: `read_docs` отдаёт не `packages/docs/ru/*.md`, а бандл
`packages/docs/dist/index.mjs`, который собирает `scripts/bundle-docs.mjs`. Поправил раздел —
запусти `pnpm --filter @mapward/docs build`, но в живом MCP он всё равно будет старым до
перезапуска расширения. Проверяется `grep` по `dist/index.mjs`, а не вызовом
(проверено 2026-09-20 на разделе `directives`).

И то же самое с интерфейсом карты: правка в `packages/abstract-react-client/src` доезжает до
вебвью через один бандл — `apps/vscode-extension/dist/webview.mjs`. Дошла ли — проверяется
`grep` по нему после `pnpm build`, а не глазами на карте: глазами видно только после
перезапуска окна (проверено 2026-09-21 на фильтре групп в хлебных крошках).

С 2026-09-21 у этого есть второй источник: расширение можно поставить в редактор насовсем
(`pnpm --filter @mapward/vscode-extension install-local`, решение
[0030](../docs/decisions/0030-local-distribution.md)). Тогда живой MCP отвечает из
`~/.vscode/extensions/mapward.mapward-<версия>/dist`, и `pnpm build` в репозитории его не
трогает **вовсе** — не «до перезапуска», а никогда: нужна пересборка пакета и переустановка.
Какая из двух сборок сейчас отвечает, по ответу не видно; смотреть — метрика
«Пакет и что стоит в редакторе» на вкладке «Публикация» объекта расширения. И два окна на одну
карту (установленное плюс Extension Development Host) — это два писателя, чего
[0009](../docs/decisions/0009-mcp.md) не предполагает.

Обратная ловушка: текст этапа читается с диска, поэтому промпт бывает **новее** сервера. 2026-09-23
этап «Брейншторм» велел отдать реплику `finish_directive { reply }`, сервер вызов принял, а в
файл ничего не дописал; после пересборки и перезапуска (в тот же день, 14:53) `reply` заработал.
После такого вызова проверяй хвост директивы `read_index { file, tail }`, и если реплики нет —
дописывай руками. Свежесть сборки видно в `list_maps`, поле `build` (`builtAt`, `stale`).

Проверено 2026-09-20 на поле `prompt` (решение
[0018](../docs/decisions/0018-agent-memory.md)): тесты и сборка зелёные, а
`run_directive` отдавал промпт без нового блока, пока расширение не перечитали.
