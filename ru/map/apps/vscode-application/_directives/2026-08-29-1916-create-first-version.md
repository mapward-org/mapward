
## Реализуем первую версию расширения

Поведение целиком описано в `ru/docs/requirements.md` — сценарии «Открыть карту», «Объект»,
«Метрики», «Уведомления», «Вотчеры». Модель — решения `0002`–`0007`.


Что правим:

- Внутри папки расширения создаём файл `Architecture.md` в который запиши всё что касается архитектуры из этого файла
- Добавь метрику архитектура со ссылкой на этот док в этот объект
- Напиши план реализации по пунктам в `PLAN.md` (тоже в расширении) и добавь метрику ссылку на него
- Сделай первый пункт плана — база расширения


### Архитектура

```
src/
  apps/ - Файлы точки входа в расширения. Не реализуют бизнес функции связывают фичи друг с другом и запускают
   webview/
   extension/
  features/ - Крупные !независимые единицы функций
   feature/
    index.extension.ts - public api, всё что может использоваться снаружи без * в импортах всё явно (всё что нужно экстеншену)
    index.webview.ts - Тоже что и index.extension.ts только для webview
    compose/ - Точки входа в модуль (компоненты хуки, функции) не содержит логики, но композирует model, ui, adapters pure-model здесь нет чистых реакт хуков и дивов
    _sub-module/ - Подмодуль
      ...
    model/ - Управление внутренним состоянием модуля (тем которым он владеет)
    adapters/ - Адаптеры к внешнему состоянию модуля, которым он не владеет
    ui/ - Компоненты которые могут содержать состояние отображения не больше в первую очередь вёрстку
    pure-model/ - Типы и чистые функции

  kernel/ - Связующий слой фич. тут только типы чистые функции порты и контексты
  shared/ - Переиспользуемые модули, без чётких правил но декомпозированы по low coupling high cohesion и не содержат бизнес информации
   
     

```

Хочется инкапсулировать по фичам а не по рантайму

#### Правило импортов приложения

`apps -> features (feature|feature) -> kernel -> shared`
(Импорты через уровень разрешены)

#### Правило импортов фичи

`compose -> (model|adapters|ui) -> pure-model`

Важно! файлы model adapters ui не могут импортировать друг друга, связь через compose 

Подмодули могут использовать pure-model родителя, родитель может использовать дочерний модуль только внутри compose
`compose -> _submodule -> pure-model`

#### Об изоморфности

Зависимости от runtime только в адаптерах. Так удобно контролировать связность и потом подменять

model - не имеет связей внутри, поэтому разные рантаймы через разные compose будут тянуть разные model

То есть фича инкапсулирует срез, и код внутри изоморфный
