## Проверка

Всё, на что директива ссылается, существует: `StatusMark`/`LinkNode`/`TreeNode`
(`core/src/model/display.ts`), `FileTree` со свёрнутыми папками (`useState(false)`) и
`StatusDot`, `ShellPort`, `watchMetrics`, подъём вверх по дереву в `find-maps.ts` и
`workspace.ts`, `exclude` на `read-dir` у метрики «Файлы». Противоречия ниже — не в ссылках,
а в ответах.

### «Отдельный от StatusMark механизм» и «дисплей просто принимает цвет» — это разное

Первый ответ говорит: git ведём отдельным каналом, чтобы «файл изменён» не затирало «тест
упал». Второй: дисплей принимает цвет, а смысл цвета выдаёт коллектор или трансформ. Но цвет
у узла уже есть — это `StatusMark.color`, и он занят метрикой. Если git красит через него,
канал не отдельный и затирание вернулось; если не через него, у узла нужен второй цвет.

> [AI] Какой из двух ответов главнее: git получает **своё поле** у узла рядом со `StatusMark`
> (тогда дисплей рисует две пометки разного рода), или git пишется **в тот же `color`**, и мы
> соглашаемся, что метрика и git за него конкурируют?

### Git в `collect` протухнет раньше, чем успеет перекраситься

Вотчер на `.git` с дебаунсом обещает перекраску сразу по сохранению. Но значение метрики живёт
в сторе (0013) и не пересобирается, пока свежо, — это требование «Свежее значение не
пересобирается на каждый взгляд» со сроком из `collectorsStaleTime`. Git, вшитый в значение,
обновится не по вотчеру, а по расписанию метрики: у `manual` — никогда.

> [AI] Что делает вотчер `.git`, если git лежит внутри значения: дёргает **пересбор всех
> метрик объекта** (дорого, и `manual` так не трогают), или git всё-таки накладывается поверх
> готового значения, а в `collect` его нет?

### Если git «везде, где `link`», его считает не коллектор

Коллекторов несколько видов, и `script` с `agent` отдают узлы произвольной формы. «Везде, где
`link`» при git-в-`collect` означает, что каждый такой коллектор — включая чужие скрипты —
обязан сам звать git и сам заполнять пометку. Это ровно то, чего первый ответ хотел избежать.

> [AI] Git — это **отдельная стадия пайплайна** после коллекторов, которая проходит по узлам с
> `link` и проставляет пометку независимо от того, кто узлы породил? Или всё же каждый
> коллектор сам, и тогда «везде» сужается до наших встроенных?

### Букве рядом с именем негде лежать

`LinkNode` — это `label`, `link`, `description` плюс `StatusMark`; поля под букву нет, а
`status` занят четырьмя состояниями метрики по 0010. Значит формы отображения из 0004
расширяются — и это правка решения, а не деталь реализации.

> [AI] Заводим у узла одно git-поле (скажем, `git: { letter, color }`), или две отдельные
> строки в `StatusMark`-стиле? И правим 0004 отдельным решением или дополняем его?

### `M/A/D/U/C` — это буквы редактора, а источник у нас порцелейн

Директива говорит «сохраняем тот же язык», и набор взят из vscode, где `U` — untracked, а `C`
— conflict. У `git status --porcelain` те же буквы значат другое: `C` — copied, `U` — unmerged,
а неотслеживаемый файл приходит как `??`. Плюс отказ от разделения staged/unstaged схлопывает
`A` (бывает только staged) и `M` в двухсимвольном коде `XY`.

> [AI] Правило перевода порцелейна в буквы пишем явно в требовании (`?? → U`, `XY` → одна
> буква по приоритету)? И какой приоритет у `MM` — staged или рабочее дерево?

### Ответ «и в MCP» перестаёт быть выбором, если git в значении метрики

Последний ответ добавляет git в `read_object`. Но если git лежит внутри значения метрики, он
туда приедет сам, без отдельной работы, — и наоборот, не приедет, если его нет в значении.
Отдельного решения тут нет: оно уже принято ответом про `collect`.

> [AI] Тогда вопрос обратный: агенту git нужен **в каждой метрике с узлами**, или отдельным
> компактным ответом (список изменённых путей объекта) — чтобы `metrics: []` не означало «git
> тоже не пришёл»?

### Игнорируемое серым — пока реплика, а не решение

«Хорошая идея» осталась без ответа «делаем». Технически это другой вызов: `--ignored` заметно
дороже на большом репозитории, а у `read-dir` уже есть свой `exclude` (`node_modules`, `dist`),
который прячет почти всё игнорируемое ещё до того, как git о нём спросят.

> [AI] Игнорируемое — в этот прогон или отдельной директивой потом?

### Файл вне git и чужой репозиторий: молча — это точно молча?
