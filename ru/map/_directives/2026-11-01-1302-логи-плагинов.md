## Задача

Ход выполнения экшона, метрики или вызова плагина сейчас толком негде посмотреть: прогон пишется
только при запуске через экшон, stderr плагина держится в памяти хвостом, вызовы MCP не пишутся
вовсе. Нужны логи каждого плагина и самого mapward в `.mapward/`, которые читают и человек, и
агент.

## Решено

- **логи** — файлы в `.mapward/logs/`: файл на плагин и `mapward.log` для платформы и входов MCP; агенты читают их путём, отдельного инструмента MCP нет
- **формат** — JSON Lines, строка несёт трейс, номер вызова, объект, плагин, метод, время и вид записи
- **кто пишет** — платформа; плагин зовёт свой `log`, платформа приклеивает контекст вызова
- **хранение** — 10 МБ на файл плюс одна предыдущая копия; старые прогоны не нужны, логи смотрят по последним
- **запуск — это трейс** — логи и запуски разделены: логи льются в файлы, запуск — трейс, поток логов фильтруется по трейсу
- **прогоны** — остаются понятием и экраном, но своего хранилища нет: запись о прогоне — строки начала и конца трейса в логе
- **экран прогонов** — интерфейс к логам с фильтрами: по объекту, по плагину на объекте; «все логи» и «по плагину все» — дополнительный вид для отладки, а не основной
- **трейс сквозной** — вложенные вызовы плагинов, процессы, агент и его вызовы MCP идут в трейсе того, кто их начал
- **отмена** — любой идущий вызов и трейс можно отменить; обёртки не нужно, это отписка; дока плагинов показывает хук отмены и советует проверять его и писать логи почаще
- **красная точка метрики** — открывает трейс, если он ещё в логе; иначе причина видна в значении метрики

## План

**1. solution: сквозной трейс.** Любой вход в платформу заводит трейс: кнопка экшона, строка
списка, `run_action` и другие инструменты MCP, `mapward action`, сбор метрики. Трейс — номер, кто
завёл и на каком объекте. Каждый вызов метода плагина идёт внутри трейса со своим номером вызова
и помнит родителя. Трейс едет вниз сам: вызов другого плагина и просьбы к платформе — в трейсе
вызова, откуда их сделали; процессам `shell` и `agent` — переменной окружения; MCP принимает трейс
с подключения (`agent` запускает Claude с конфигом MCP, где трейс — заголовок). Вызов MCP без
трейса заводит свой. Отмена трейса снимает все его идущие вызовы, вложенные тоже. Прогон экшона —
трейс, заведённый кнопкой; его номер — номер прогона.

**2. platform: контекст вызова в API плагина.** Метод получает свой `ctx` на вызов — те же поля
плюс сам вызов: `ctx.log(...)` — ход, `ctx.log.error(...)` — ошибка, `ctx.output(...)` — вывод,
`ctx.step(имя)` — начался шаг; платформа пишет их в файл плагина с трейсом, номером вызова,
объектом и методом. `ctx.signal` — сигнал отмены вызова; отписка от потока по-прежнему отмена.
`ctx.plugin(...)`, `ctx.editMap` и другие просьбы из такого `ctx` уходят в трейсе вызова. У
`init` и `dispose` — `ctx` процесса: его `log` и stderr ложатся в файл плагина без вызова.
Сообщения хода в потоке (`progress: step | out | log`) уходят, в потоке только итог; `shell`,
`agent` и копии встроенных плагинов в карте переводятся на новое API. Дока плагинов показывает
`ctx.signal` и `ctx.log` в первом примере.

**3. software: логи и трейсы на сервере вместо хранилища прогонов.** Хранилище прогонов уходит,
появляются два модуля. Логи — единственный писатель в `.mapward/logs/`: файл на плагин и
`mapward.log`, JSON Lines, 10 МБ с одной копией `.1`, запись пачками, поток строк по фильтру
(трейс, объект, плагин) — хвост из файлов, потом новые. Трейсы — память об идущих: заводит трейс,
ведёт дерево вызовов, по отмене снимает дерево, сообщает ленте; начало и конец трейса (кто, объект,
данные формы, конфиг, статус, итог) пишет в лог — этим прогон и сохраняется. Хост плагинов не копит
stderr в памяти: stderr и `ctx.log` уходят в лог, причину падения объясняет хвостом из лога.
Экшоны запускаются через трейсы; список прогонов объекта — строки начала трейса по его адресу.
Трейс без строки конца после перезапуска окна показывается прерванным.
