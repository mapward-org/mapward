# Экшоны

Экшон — папка в `_actions/` с `config.json`: то, что над объектом делают по кнопке. Метрика
читает, экшон пишет — выпускает версию, прогоняет проверку, перезапускает упавший тест. Своего
вывода у него нет: что он сделал, видно в метриках объекта.

```ts
type Action = {
  label?: string
  description?: string
  extends?: string                         // mapward:// адрес другого экшона
  confirm?: boolean                        // спросить перед запуском, даже с полной формой
  timeout?: number                         // мс на весь прогон
  inputs?: Record<string, ActionInput>     // поля формы
  runners?: ActionRunner[]                 // шаги по порядку
  refreshes?: string[]                     // ключи метрик объекта, пересобрать после успеха
}
```

Как и у метрики, любое поле может приехать от прототипа или от общего экшона по `extends`.
Свой экшон с тем же ключом перекрывает прототипов; поля формы при этом сливаются по имени —
наследник, добавивший одно поле, не теряет остальных. Подстановки `${{ … }}` разрешаются по
объекту, на котором экшон нажали, а не там, где лежит файл: общий экшон берёт пути и имена у
того, кто его запустил.

## Шаги

Шаги идут по порядку, следующий — после того, как предыдущий сделал своё. Упал один — прогон
кончается неудачей, остальные не запускаются.

| Вид | Что делает |
| --- | --- |
| `script` | команда оболочки из корня карты; `run` — сама команда |
| `prompt` | агент в headless-режиме; `prompt` — текст, `permissions` — что ему можно |

Вид, которого инструмент не знает, — ошибка шага, а не карты.

Скрипт получает объект так же, как скрипт метрики, — переменными `MAPWARD_OBJECT_PATH`,
`MAPWARD_MAP_PATH`, `MAPWARD_OBJECT_NAME`, `MAPWARD_OBJECT`. Промпт-шаг работает из корня проекта,
а не карты: экшону чаще нужен код, чем карта. Агенту в начало промпта кладётся объект, в конец —
данные формы.

Нужно, чтобы работа шла в своей сессии, с контекстом и перепиской, — это директива, а не экшон.

## Права агента

Метрике разрешений не нужно: она читает. Экшону нужно писать, поэтому промпт-шаг говорит сам, что
агенту можно:

```json
{ "kind": "prompt", "prompt": "…", "permissions": ["Read", "Edit", "Bash(pnpm changeset:*)"] }
```

`"permissions": "bypass"` снимает вопросы целиком. Без поля агент может только читать — правку и
команду ему некому одобрить. Список лучше обхода: экшон из чужой карты не должен получать всё по
умолчанию.

## Форма

Почти всякому экшону нужны данные. Поля описываются в `inputs`, с теми же названиями, что у
ручного запуска GitHub Actions:

```json
"inputs": {
  "level": { "type": "choice", "options": ["patch", "minor", "major"], "required": true },
  "dry": { "type": "boolean", "description": "только показать, что уйдёт" },
  "note": { "type": "string", "multiline": true, "default": "${{ mapward://~#name }}" }
}
```

`type` — `string`, `boolean`, `number` или `choice`; без него строка. `default` проходит
подстановку, как весь конфиг. Флажок без значения — это «нет», а не пропуск.

Поля проверяет сервер, а не форма: иначе агент и терминал обходили бы обязательные. Не хватает
обязательного, значение не того вида или поле с чужим именем — прогона нет, в ответ приходят
ошибки по полям. Всё заполнено и `confirm` не просили — экшон запускается сразу, без формы.

До скрипта данные доезжают JSON-ом во входе и переменными: `MAPWARD_INPUTS` целиком и
`MAPWARD_INPUT_<ИМЯ>` по полю, имя в верхнем регистре. В текст промпта и в команду скрипта они
попадают выражением `${{ inputs.<имя> }}`. Подстановка карты такие выражения не трогает: данные
приходят при запуске, а не при чтении карты.

## Прогоны

Прогон — кто запустил, когда, с какими данными, шаги по порядку с логом и выводом каждого, итог.
Запускают экшон кнопкой на карте, со строки дисплея, агент через MCP и человек из терминала, и
всё это видно одинаково.

Прогоны одного экшона идут параллельно: у экшона параметры, и запустить его на разные значения
разом — обычное дело. У каждого свой номер и своя остановка. `timeout` снимает прогон, если он
идёт дольше, и прогон краснеет с причиной «время вышло».

После успеха пересобираются метрики из `refreshes`: старое значение рядом со свежим запуском
висеть не должно.

Прогоны — операционка, а не история проекта. Они лежат в `.mapward/runs/` в корне карты, по
двадцать последних на экшон или метрику, и в git не попадают: в `.mapward/` карта сама кладёт
`.gitignore` со звёздочкой. Прогоны метрик пишутся туда же, поэтому у метрики видно, как прошёл
каждый её сбор. Прогон, который шёл во время перезапуска окна, возвращается остановленным:
дописать его некому.

Смотрят прогоны на экране прогонов объекта: слева список, свежие сверху, справа выбранный —
конфиг после подстановок, данные формы, шаги с логами и «остановить», пока он идёт. Общего
списка на всю карту нет: карта делится на зоны, и чужие прогоны там — шум.

## Где кнопки

У объекта в шапке — все его экшоны списком с поиском: от прототипа их бывает много. Конкретный
экшон ставится в раскладку сетки ключом, как метрика, и рисуется там кнопкой. Поэтому ключи
метрики и экшона одного объекта совпадать не должны — совпадение показывается ошибкой.

Строка списка и узел дерева несут поле `action`:

```json
{ "label": "tests/map.test.ts", "link": "tests/map.test.ts", "status": "fail",
  "action": { "run": "rerun-test", "inputs": { "file": "tests/map.test.ts" } } }
```

`run` — ключ экшона того объекта, на котором висит метрика, или полный адрес экшона. У строки
справа появляется кнопка запуска, а клик по самой строке по-прежнему ведёт по `link`: упавший
тест нужно и открыть, и перезапустить. Экшона, которого нет, — ошибка этой строки, а не всей
метрики.

Компонент-дисплей получает экшоны объекта и запуск в пропсах, а кнопку — готовым кусочком набора.

## Инструкция — не экшон

Текста «как правильно сделать» в `_actions/` больше нет: markdown там не читается. Инструкция для
агента — это дока, и на неё ссылается метрика объекта.
