# Экшоны

Экшон — папка в `_actions/` с `config.json`: кнопка с формой над изменяющим методом
[плагина](plugins.md). Метрика читает, экшон пишет — выпускает версию, прогоняет проверку,
перезапускает упавший тест. Своего вывода у него нет: что он сделал, видно в метриках объекта —
они подписаны на свои плагины и обновятся сами.

```ts
type Action = {
  label?: string
  description?: string
  extends?: string                         // mapward:// адрес другого экшона
  confirm?: boolean | string               // true — форма даже полная; текст — вопрос перед запуском
  plugin: string                           // папка плагина: от этого config.json или абсолютная
                                           // (подстановкой: "${{ mapward:// }}/_plugins/shell")
  method: string                           // изменяющий метод плагина
  params?: Record<string, unknown>         // заданные параметры метода; в форму не попадают
  inputs?: Record<string, ActionInput>     // поля формы явно — вместо схемы метода
  component?: string                       // своя форма: .tsx от этого config.json
}
```

```json
{
  "label": "Поставить метку",
  "confirm": true,
  "plugin": "../../../_plugins/git",
  "method": "tag",
  "params": { "repo": "${{ mapward://~#props.codePath }}" }
}
```

Как и у метрики, любое поле может приехать от прототипа или от общего экшона по `extends`.
Свой экшон с тем же ключом перекрывает прототипов; поля формы и параметры при этом сливаются по
имени — наследник, добавивший одно поле, не теряет остальных. Путь `plugin` считается от папки
того `config.json`, где он написан; путь, который начинается подстановкой, —
`${{ mapward:// }}/_plugins/shell`, — абсолютный после неё и годится в любом слое. Подстановки `${{ … }}` разрешаются по объекту, на котором
экшон нажали, а не там, где лежит файл: общий экшон берёт пути и имена у того, кто его запустил.

Для MCP экшон — именованный ярлык на метод с заданными параметрами: `run_action` зовёт метод через
платформу и пишет прогон в историю. Агент может позвать и сам метод, `call_plugin`, — тогда
истории нет.

Нужно, чтобы работа шла в своей сессии, с контекстом и перепиской, — это директива, а не экшон.

## Форма

Форма строится по JSON-схеме параметров метода из самоописания плагина (`describe_plugin`):
каждое свойство, которого нет в `params`, — поле. Заполненное человеком ложится в аргументы рядом
с `params`. Из схемы берутся `type` (`string`, `number`/`integer`, `boolean`), `enum` — выбор из
вариантов, `description`, `default` и `required`; `"format": "multiline"` у строки — многострочное
поле. Объекты, массивы и свойства без типа в простую форму не ложатся — их задают в `params`.

Когда схемы мало, поля пишутся явно, в `inputs`, с теми же названиями, что у ручного запуска
GitHub Actions:

```json
"inputs": {
  "level": { "type": "choice", "options": ["patch", "minor", "major"], "required": true },
  "dry": { "type": "boolean", "description": "только показать, что уйдёт" },
  "note": { "type": "string", "multiline": true, "default": "${{ mapward://~#name }}" }
}
```

`type` — `string`, `boolean`, `number` или `choice`; без него строка. `default` проходит
подстановку, как весь конфиг. Флажок без значения — это «нет», а не пропуск. С `inputs` данные
формы приходят методу одним полем — `inputs`: так их ждут `shell` и `agent`.

Поля проверяет сервер, а не форма: иначе агент и терминал обходили бы обязательные. Не хватает
обязательного, значение не того вида или поле с чужим именем — прогона нет, в ответ приходят
ошибки по полям. Заданное в `params` формой не перебивается: такого поля в ней нет. Всё
заполнено и `confirm` не просили — экшон запускается сразу, без формы.

## Своя форма

Когда полей по схеме мало — нужен выбор из списка, который знает плагин, предпросмотр, связанные
поля, — форму пишут сами: `"component": "./form.tsx"`, путь от этого `config.json`, как у
метрики-компонента. Собирается тем же сборщиком и получает тот же `@mapward/component` —
`usePlugin`, `useQuery`; кирпичи `views` — относительным импортом.

```tsx
import type { ActionFormProps } from "@mapward/component";

export default function Form({ params, submit, cancel, sending }: ActionFormProps<{ level?: string }>) {
  return (
    <div className="flex gap-2">
      {["patch", "minor", "major"].map((level) => (
        <button key={level} disabled={sending} onClick={() => submit({ level })}>
          {level}
        </button>
      ))}
      <button onClick={cancel}>отмена</button>
    </div>
  );
}
```

| Пропс | Что это |
| --- | --- |
| `params` | значения на старте: переданные запуском и умолчания полей |
| `schema` | JSON-схема параметров метода из самоописания плагина; у экшона с `inputs` её нет |
| `fields` | поля, какими их нарисовала бы обычная форма |
| `errors` | ошибки сервера по полям после неудачной отправки |
| `sending` | отправлено, ждём «принято» |
| `action` | `key`, `address`, `label`, `description` |
| `submit(values)` | отправить: значения ложатся поверх переданных запуском, дальше — как у обычной формы |
| `cancel()` | закрыть форму |

Своя форма открывается всегда, даже когда всё заполнено: её написали, чтобы её видели. Рамку,
заголовок и отказ сервера рисует карта, поля и кнопки — компонент. Проверяет значения по-прежнему
сервер, вопрос `confirm` — после `submit`, как у обычной формы. Агент и терминал своей формы не
видят: им — поля по схеме.

## Вопрос перед запуском

`confirm: true` открывает форму, даже когда она заполнена целиком: кнопка формы и есть
подтверждение. Этого хватает, когда форма сама говорит, что сейчас произойдёт, — уровень версии,
ветка. Когда не говорит, `confirm` пишется текстом вопроса, с данными формы:

```json
"confirm": "Удалить ${{ inputs.path }} насовсем?"
```

Тогда перед самым запуском открывается отдельное окно: вопрос, кнопка с подписью экшона и
«Отмена». Фокус стоит на «Отмене», поэтому Enter по привычке ничего не запускает. Есть
незаполненные поля — сначала форма, вопрос после неё, уже с тем, что в неё вписали.

Агент через MCP окна не видит. `run_action` такого экшона без `confirmed: true` прогона не
заводит, а отвечает тем же вопросом с подставленными данными: спросить человека должен агент.

## Ход и итог

Метод отвечает потоком, и окно прогона показывает его по мере прихода. Значения особого вида —
сообщения о ходе, их платформа пишет в шаги прогона:

| Сообщение | Что значит |
| --- | --- |
| `{ "progress": "step", "name": "…" }` | начался шаг; предыдущий кончился успехом |
| `{ "progress": "out", "text": "…" }` | строка вывода шага |
| `{ "progress": "log", "text": "…" }` | строка хода и ошибок шага |

Всё остальное, что метод отдаёт, — итог: в прогоне остаётся последнее такое значение. Метод,
который шагов не называет, получает один шаг — плагин и метод. Ошибка потока — прогон упал с её
текстом; конец потока — успех. Сам плагин об истории не знает: зовут его и мимо экшона.

## Встроенные `shell` и `agent`

Команды и агент — встроенные плагины. Они лежат в карте по своему месту, `_plugins/shell` и
`_plugins/agent`; нет их там — платформа доставит сама, на первый запуск. Это код проекта:
правьте под себя.

| Метод | Что делает |
| --- | --- |
| `shell.run` | команда оболочкой: `command`, `cwd`, `env`, `input`, `timeout` |
| `shell.steps` | шаги по очереди: `{ kind: "script", command }` или `{ kind: "prompt", prompt, permissions }` |
| `agent.run` | один вопрос агенту: `prompt`, `permissions`, `cwd`, `env`, `timeout` |

**`shell.run`** — рабочая папка по умолчанию — папка карты. Данные формы доезжают до команды
выражением `${{ inputs.<имя> }}`, переменными `MAPWARD_INPUTS` целиком и `MAPWARD_INPUT_<ИМЯ>` по
полю (имя в верхнем регистре) и JSON-ом в stdin. Объект — подстановками в `command` и `env`:
сам плагин не знает, на каком объекте нажали кнопку. Вывод — строками по мере появления,
ненулевой код — ошибка с хвостом stderr.

**`agent.run`** — агент в headless-режиме, `claude -p`, промпт в stdin. Работает из корня
проекта, а не карты: экшону чаще нужен код. Данные формы плагин дописывает в конец промпта. Ход
агента — «→ Read файл», «→ Bash команда», текст — идёт строками лога, ответ — выводом и итогом
`{ answer }`.

Экшону нужно писать, поэтому он говорит сам, что агенту можно:

```json
{
  "plugin": "${{ mapward:// }}/_plugins/agent",
  "method": "run",
  "params": {
    "prompt": "Опиши изменение пакета ${{ mapward://~#props.packageName }} changeset-ом…",
    "permissions": ["Read", "Write", "Bash(git add:*)", "Bash(git commit:*)"]
  }
}
```

`"permissions": "bypass"` снимает вопросы целиком. Без поля агент может только читать — правку и
команду ему некому одобрить. Список лучше обхода: экшон из чужой карты не должен получать всё по
умолчанию.

Экшон со своей формой у `shell` и `agent` пишет поля в `inputs`, а если формы нет вовсе — пустые
`{}`: иначе форма соберётся по схеме метода и спросит `cwd` и `env`.

```json
{
  "label": "Удалить",
  "confirm": "Удалить ${{ inputs.path }} насовсем?",
  "inputs": { "path": { "type": "string", "required": true } },
  "plugin": "${{ mapward:// }}/_plugins/shell",
  "method": "run",
  "params": { "command": "node file-ops.mjs delete" }
}
```

## Прогоны

Прогон — кто запустил, когда, с какими данными, шаги по порядку с логом и выводом каждого, итог.
Запускают экшон кнопкой на карте, со строки списка, агент через MCP и человек из терминала, и
всё это видно одинаково. История — за платформой и только у вызовов через экшон: платформа и так
маршрутизирует вызов и пишет вызов, сообщения и итог.

Прогоны одного экшона идут параллельно: у экшона параметры, и запустить его на разные значения
разом — обычное дело. У каждого свой номер и своя остановка. Остановка — отписка от вызова:
плагин видит отмену и гасит своё, `shell` и `agent` снимают процесс вместе с детьми.

Прогоны — операционка, а не история проекта. Они лежат в `.mapward/runs/` в корне карты, по
десять последних на экшон, и в git не попадают: в `.mapward/` карта сама кладёт `.gitignore` со
звёздочкой. Прогонов метрик там нет: история — только у экшонов. Прогон, который шёл во время
перезапуска окна, возвращается остановленным: дописать его некому.

Смотрят прогоны на экране прогонов объекта: слева список, свежие сверху, справа выбранный —
конфиг после подстановок, данные формы, шаги с логами, итог и «остановить», пока он идёт. Общего
списка на всю карту нет: карта делится на зоны, и чужие прогоны там — шум.

Лог шага растёт по ходу, а не появляется в конце. Окно лога держится у конца, пока его не
отмотали вверх. На диск прогон пишется, когда кончился.

## Где кнопки

У объекта в шапке — все его экшоны списком с поиском: от прототипа их бывает много. Конкретный
экшон ставится в [раскладку](index-format.md#раскладки) вкладки или в компонент кнопкой из
кирпичей `views` — `<ActionButton action="…" />` — или своей: `useAction` из `@mapward/component`
даёт `{ run, running, label, description, missing }`.

Строка списка и узел дерева несут поле `action`:

```json
{ "label": "tests/map.test.ts", "link": "tests/map.test.ts", "status": "fail",
  "action": { "run": "rerun-test", "inputs": { "file": "tests/map.test.ts" } } }
```

`run` — ключ экшона того объекта, на котором висит метрика, или полный адрес экшона. У строки
справа появляется кнопка запуска, а клик по самой строке по-прежнему ведёт по `link`: упавший
тест нужно и открыть, и перезапустить. Экшона, которого нет, — ошибка этой строки, а не всей
метрики.

Когда экшонов у строки несколько, они идут списком в `actions` — это меню строки:

```json
{ "label": "map.test.ts", "link": "tests/map.test.ts",
  "actions": [{ "run": "file-rename", "inputs": { "path": "tests/map.test.ts" } },
              { "run": "file-delete", "inputs": { "path": "tests/map.test.ts" } }] }
```

Меню открывается кнопкой «⋯», которая появляется у строки при наведении, и правым кликом по
строке — это одно меню. Роли у полей не пересекаются: `action` — кнопка прямо на строке,
`actions` — меню, и у строки бывает и то, и другое. Экшона из меню, которого нет, — ошибка этого
пункта.

Компонент метрики ставит кнопку экшона кирпичом `ActionButton` или рисует свою на `useAction`:
запуск идёт тем же путём, что из шапки, — форма, вопрос, история прогонов. Кирпичи `List` и
`FileTree` плагина `views` рисуют и кнопки, и меню строк: `action` и `actions` у пункта — те же
поля.

## Инструкция — не экшон

Текста «как правильно сделать» в `_actions/` больше нет: markdown там не читается. Инструкция для
агента — это дока, и на неё ссылается метрика объекта.
