# Плагины и метрики-компоненты

Метрика — компонент, который берёт данные у плагина — долгоживущего процесса со своим
состоянием. Готовые виды — список, дерево, ссылка, статус, текст — тоже компоненты, встроенного
плагина [`views`](#готовые-виды-views); данные им дают встроенные `shell`, `files` и `agent`.

## Плагин

Плагин — папка с `index.ts` (или `.tsx`, `.js`), которая по умолчанию экспортирует определение:

```ts
import { definePlugin } from "@mapward/plugin";
import { defer, map } from "rxjs";
import { Type } from "typebox";

export default definePlugin({
  description: "граф кода",
  activation: { idle: 10 * 60_000 },
  init: async (ctx) => {
    /* прогрев: построить состояние до первого вызова */
  },
  dispose: async (ctx) => {
    /* сохранить кэш; вежливость, а не гарантия */
  },
  methods: {
    deps: {
      description: "зависимости пакета",
      params: Type.Object({ path: Type.String() }),
      result: Type.Array(Type.String()),
      // args: { path: string } — тип выведен из params; значения сверяются с result.
      run: (args) => defer(() => depsOf(args.path)).pipe(map((deps) => deps.toSorted())),
    },
    rebuild: { kind: "mutation", run: () => defer(() => rebuildGraph()) },
  },
});
```

- **Процесс — один на плагин на карту.** Поднимается на первое обращение — вызов из компонента,
  запрос агента, `describe_plugin`. Гаснет после простоя (по умолчанию пять минут;
  `activation.idle: false` — не гаснет). Правка любого файла в папке плагина вне `node_modules`
  перезапускает процесс, и живые подписки переезжают в новый сами.
- **Каждый метод возвращает `Observable` из rxjs.** Запрос это или подписка, решает плагин:
  одиночный ответ — поток из одного значения (`of(значение)`, `defer(async () => …)`), живой —
  `new Observable(…)` или операторы над `ctx.object` и `createVfs`. Отписка вызывающего — это
  отмена: срабатывает teardown потока.
- **rxjs и typebox даёт платформа** — как `@mapward/plugin`: сборщик подставляет `rxjs`,
  `rxjs/operators`, `typebox` и его подпути (`typebox/value`, `typebox/compile`, …) той же копией,
  на которой живёт рантайм. Ставить их плагину не надо, второй копии в сборке нет, и
  `ctx.object(…) instanceof Observable` верно. В `package.json` проекта их держат ради типов —
  `@mapward/plugin` тянет оба.
- **Схема — это и тип, и проверка.** `params` и `result` — JSON-схема, обычно typebox
  (`Type.Object(…)`): `definePlugin` выводит из `params` тип `args`, а значения потока сверяет с
  `result`. Платформа проверяет аргументы по `params` до `run` и отвечает ошибкой с путём до поля
  (`аргументы deps не по схеме: /path: must be string`) — метод не зовётся. Схему можно писать и
  руками; без схемы тип `args` — из подписи `run`. Сообщения о ходе (`RunMessage`) идут мимо
  `result`.
- **TypeScript собирает платформа** — тем же esbuild, что компоненты. Запускает node самой
  платформы: в редакторе — node VS Code, в консоли — тот, что запустил `mapward`. В проекте не
  нужны ни `tsx`, ни шаг сборки. Сборка ложится в `.mapward/plugins/` карты, вне git.
- **Рабочая папка процесса — папка плагина.** stdout занят протоколом, поэтому `console.log`
  уходит в stderr — в лог плагина.
- **Скорость — забота плагина.** Платформа не ставит таймаутов, очередей и форматов кэша. Срок
  ожидания называет тот, кто зовёт: MCP ждёт 30 секунд, если агент не назвал свой.
- **Свои зависимости** — `package.json` в папке плагина; `@mapward/plugin` подставляет платформа.

## Контекст `ctx`

Метод получает `(args, ctx)`, `init` и `dispose` — `(ctx)`. Глобального API нет: метод
тестируется с поддельным контекстом.

| Поле | Что это |
| --- | --- |
| `ctx.map` | карта процесса: `name`, `mapPath`, `basePath` |
| `ctx.pluginDir` | своя папка |
| `ctx.resolve(адрес, от?)` | путь из адреса без решётки, синхронно: `mapward://x`, `mapward://@/src`, `mapward://~/…` от объекта |
| `ctx.log(…)` | строка в лог плагина |
| `ctx.object(адрес)` | объект после мерджа и подстановок — потоком, с изменениями карты |
| `ctx.children(адрес)` | дети объекта, так же |
| `ctx.tree(адрес, глубина)` | поддерево от адреса, как его видит платформа: объект с потомками на `глубина` уровней (`0` — без детей, `1` — дети без внуков, `Infinity` — все), с метриками и слоями (`MapObject`), потоком. Глубина обязательна: всё под адресом платформа держит прочитанным, пока поток жив, а `Infinity` от корня — вся карта. Для тех, кто считает по карте сам |
| `ctx.plugin(путь).call(метод, args)` | другой плагин — через платформу, его процесс поднимется сам |
| `ctx.editMap(ops)` | правка карты платформой — пачка операций, как `edit_map` у агента ([MCP](mcp.md#написать-карту-методами--edit_map)): свои поля по адресу (`get`, `set` — полная замена с проверкой, `delete`) объекта, метрики, экшона, слоя и этапа; структура (`create`, `move`, `setFolder`, `copy`); сырые файлы (`readFile`, `writeFile`, `removeFile`); `check`, `installDeps`. Ложится целиком или никак; ответ — `{ ok, id, results, created, moves, copies, touched }`, `results` — ответ каждой операции. Перенос сам переписывает адрес в `_index.json` и `config.json` карты; свои файлы с адресами плагин переписывает по `moves` |
| `ctx.undoEdit(id)`, `ctx.redoEdit(id)` | отмена и повтор пачки `editMap` по номеру; файлы, поменянные мимо неё, не затираются — отказ |
| `ctx.isVscode` | платформу поднял VS Code |
| `ctx.vscode` | редактор: `openFile`, `reveal` (файл или папка в проводнике), `showMessage`, `terminal`, `executeCommand`. Без редактора обращение бросает ошибку |
| `ctx.webview` | клиент карты для отрисовки вне редактора: `{ assets, bridge }` — папка сборки вебвью и адрес моста до платформы по http. Есть только у платформы в редакторе; им рисует `screenshot` |

Объекта, который вызвал метод, в контексте нет: что нужно, передаётся в аргументах. Иначе метод
вёл бы себя по-разному в окне и у агента.

Файлы — свои и карты — плагин читает и пишет сам, через `node:fs`: он процесс на машине, и
платформа между ним и диском не стоит. Записанное модель карты увидит вотчером.

Следить за файлами помогает `createVfs(папка, { keep? })` из `@mapward/plugin` — тот же механизм,
которым платформа держит карту. Он отдаёт файлы потоками: `text$(путь)`, `list$(папка)`,
`json$(путь)`, `bytes$(путь)` — содержимое как есть, `Uint8Array` (картинка, архив), и
`stat$(путь)` — `{ size, mtimeMs }` без чтения содержимого, дешёвый сигнал «файл изменился». Нет
файла — `undefined`. Файл читается, когда на него подписались, и отпускается без подписчиков (`keep` —
сколько миллисекунд подержать после ухода последнего); вотчер один на папку и стоит, пока читается
хоть что-то; правка, записанная несколькими заходами, приходит одним изменением, а одинаковое не
повторяется. Своё записанное — `touch([пути])`, перечитать всё — `reload()`. Пока файл читается,
поток говорит `PENDING`; собирать из нескольких потоков помогают `follow`, `every`, `mapReady` и
`settle` оттуда же, остальное — операторы rxjs. Из метода поток отдавайте через
`settle()`: он пропускает только готовое, одно значение на пачку, и `PENDING` в протокол не
уходит. Так встроенный `files` строит дерево: правка файла перечитывает его и папки над ним, а не
всё дерево, — а пометки git освежает по `stat$` файлов `.git/index` и `.git/HEAD`.

```ts
import { createVfs, definePlugin, settle } from "@mapward/plugin";

export default definePlugin({
  methods: {
    settings: {
      run: (args: { path: string }) =>
        createVfs(args.path).json$(`${args.path}/settings.json`).pipe(settle()),
    },
  },
});
```

`@mapward/plugin` — только API платформы: `definePlugin`, `ctx`, протокол, проверка по схеме
(`schemaErrors`), файлы потоками (`createVfs`) и помощники потоков. Предметных операций в нём нет. Правку карты
делает платформа (`ctx.editMap`): целостность адресов — общий инвариант карты, и перенос, забывший
переписать адрес в чьём-то `extends` или `props`, сломал бы её всем. Своё мнение о карте — вьюху,
стрелки, раскладку — плагин держит у себя, как встроенный `objects-map`: он зовёт `ctx.editMap`,
а по переездам из ответа сам переписывает свой `map-state.json`. В сборку плагина пакет едет одним
файлом со всеми зависимостями, rxjs и typebox тоже — ради них `node_modules` у плагина в карте не
нужны.

## Метрика-компонент

```json
{
  "label": "Файлы",
  "component": "./view.tsx",
  "params": { "path": "${{ mapward://~#props.fullPath }}" },
  "agent": {
    "plugin": "../../../../_plugins/files",
    "method": "summary",
    "params": { "path": "${{ mapward://~#props.fullPath }}" }
  }
}
```

- `component` — `.tsx`, путь от этого `config.json` (или подстановкой, `${{ mapward:// }}/…`).
- `params` — проходят подстановку и приходят компоненту пропсом.
- `agent` — что видит агент: метод плагина с параметрами. Компонент агент не исполняет, поэтому
  запрос для агента крайне желателен — без него агенту остаются только методы плагина.

Рамки у такой метрики нет: ни шапки, ни времени сбора, ни кнопки обновления — что показать, пока
данных нет, решает компонент. Платформа ловит только падение отрисовки. Рамку с подписью, временем
и кнопкой рисуют готовые виды плагина [`views`](#готовые-виды-views).

Компонент говорит с платформой через `@mapward/component` — это API окна: хуки ниже, `useAction`
и `ObjectCard`. Готовые кирпичи — список, дерево, markdown, сетка — код встроенного плагина
[`views`](#кирпичи-views): их берут относительным импортом из `_plugins/views/bricks/`.

```tsx
import { useNavigation, usePlugin, useStream } from "@mapward/component";
import type { MetricProps } from "@mapward/component";
import type files from "../../../../_plugins/files/index.ts";
import { FileTree } from "../../../../_plugins/views/bricks/file-tree.tsx";

export default function View({ params }: MetricProps<{ path: string }>) {
  const plugin = usePlugin<typeof files>("../../../../_plugins/files");
  const tree = useStream(["files.tree", params.path], () => plugin.tree({ path: params.path }));
  const navigate = useNavigation();
  if (tree.status === "connecting") return <div>читаю файлы…</div>;
  return <FileTree items={tree.last?.children ?? []} onClick={navigate} />;
}
```

| Хук | Что делает |
| --- | --- |
| `usePlugin<typeof plugin>(путь)` | клиент плагина; путь от файла компонента. Методы — функции от аргументов, отдающие поток |
| `useQuery(ключ, () => поток)` | подписка, пока компонент на экране: `status`, `data`, `error`, `refetch`. Ошибка не стирает прошлое значение |
| `useStream(ключ, () => поток)` | каждое значение: `status` (`connecting`, `open`, `done`, `error`), `last`, `refetch` |
| `useMutation((args) => поток)` | по вызову: `run(args)`, `status`, `data`, `error`; новый запуск отменяет идущий |
| `useNavigation()` | `navigate(ссылка или пункт, { tab? })` — открыть, как любая ссылка карты: через встроенный плагин `navigation`, объект карты — переходом экрана |
| `useViewState(ключ, начальное, { expanded? })` | `[значение, задать]` — настройка смотрящего (масштаб, свёрнутая панель): её хранит хост у человека, а не в карте; переживает перезагрузку окна. `expanded` — каким ключ бывает, когда раскрыто всё: его отдаёт снимок метрики с `expand: "all"` |
| `useAction(экшон, inputs?)` | экшон по ключу своего объекта или по адресу `mapward://…/_actions/<ключ>`: `{ run(inputs?), running, label, description, missing }`. `run` — запуск тем же путём, что из шапки объекта (форма, вопрос, история прогонов); `running` — сколько прогонов идёт; `missing` — экшона нет (пока объект-владелец не пришёл, это «ещё не знаем», а не «нет») |

Компонент — обычная функция: карта сама делает его наблюдателем, и ответы плагина его
перерисовывают.

Поток метода — `Observable` из rxjs, и хуки принимают его же. Сам rxjs (`rxjs`, `rxjs/operators`)
компоненту отдаёт карта, как `react`: ставить не надо, копия одна с клиентом, так что поток метода
можно доработать прямо в хуке —
`useStream(["files.tree", path], () => plugin.tree({ path }).pipe(map((tree) => tree.children)))`.

**Ключ запроса** у `useQuery` и `useStream` — как `queryKey` в react-query: строка или массив из
JSON, сравнивается по содержимому. Он же — зависимости: поменялся ключ — новый запрос. И он же —
место в памяти карты: компонент, вернувшийся на экран (смена вкладки, переход назад), начинает с
прошлого ответа того же ключа, а не с «загружается», пока плагин отвечает заново; свежий ответ
заменяет прошлый. Ответ без подписчиков помнится 10 минут. Начинайте ключ с плагина и метода —
`["files.tree", path]`: одинаковый ключ у разных запросов на миг покажет чужое. `useMutation`
ключа не берёт и ничего не помнит.

Открыть ссылку так, как это делает карта, — `useNavigation()`: функция подходит прямо в
обработчик кирпича, `<List items={…} onClick={navigate} />`. `how.tab` — ctrl + клик по ссылке на
объект: открыть отдельным табом (хост без табов откроет обычным переходом). Ссылку разбирает
плагин `navigation` карты (`_plugins/navigation`) — поправьте его, если ссылки проекта должны
вести иначе.

`ObjectCard({ object, group?, width?, maxHeight?, actions?, draggable? })` — карточка объекта, та
же, что у пункта списка с `object`: имя со ссылкой, кнопки объекта, компактная сетка метрик его
превью. `actions` — свои кнопки в шапке; `draggable` — ручка в шапке с классом `mw-card-drag`,
за которую карточку тащит холст. Рамка карточки помечена `data-card-frame`.

### Кирпичи `views`

Готовые кирпичи — исходники `.tsx` встроенного плагина `views`, в карте — его копия
`_plugins/views/bricks/`. Это код проекта, как весь плагин: правьте под себя. Компонент берёт их
относительным импортом, и сборщик собирает их внутрь компонента; тема — переменными `--mw-*`.
Кирпичи есть, пока в карте лежит `_plugins/views` (`mapward plugin add views`); чужой плагин,
которому хватает одного-двух кирпичей, может держать их копию у себя.

| Файл | Кирпич |
| --- | --- |
| `list.tsx` | `List({ items, empty?, onClick? })` — пункты `{ label, link, description, status, git, action, actions }`; пункт с `object` — карточка объекта |
| `file-tree.tsx` | `FileTree({ items, id?, onClick? })` — дерево; `id` — под каким ключом помнить раскрытые папки у человека (`useViewState`), без него — пока дерево на экране |
| `link.tsx` | `Link({ item, onClick? })` — ссылка с точкой статуса и буквой git |
| `markdown.tsx` | `Markdown({ text, inline?, onOpen? })` — заголовки, списки, код, ссылки |
| `status-dot.tsx` | `StatusDot({ status?, color?, hint? })` |
| `display.tsx` | `Display({ kind, data, empty?, onOpen?, id? })` — данные по виду: `text`, `markdown`, `link`, `status`, `list`, `tree`, `object`; им рисуют готовые виды |
| `grid.tsx` | `Grid` — сетка раскладки группы, см. [формат индекса](index-format.md#сетка-grid) |
| `action-button.tsx` | `ActionButton({ action, inputs?, label? })` — кнопка экшона над `useAction` |
| `types.ts` | `LinkItem`, `TreeItem`, `Status`, `ActionRef` |

Кирпичи чистые и сами ничего не открывают: `List`, `FileTree`, `Link` принимают
`onClick(item, how)`, а `Markdown` и `Display` — `onOpen(link, how)`; без них клик ничего не
делает. С платформой они говорят только через `@mapward/component`: экшоны строк — `useAction`,
пункты-карточки — `ObjectCard`, раскрытые папки — `useViewState`.

Кроме `params`, `object` и `metric` компонент получает `compact` — он стоит в превью объекта и
места мало — и `openTab()`, если метрику можно открыть отдельным табом.

## Шаблоны метрик

Плагин объявляет свои виды метрики в `templates` — платформа показывает их в `describe_plugin`, и
по ним метрику пишут короткой формой `{ label?, plugin, template, params }`:

```ts
export default definePlugin({
  templates: {
    list: {
      component: "list.tsx", // от папки плагина
      description: "список строк",
      params: Type.Object({ source: Type.Optional(Type.Unknown()) }), // JSON-схема params
      agent: { param: "source" }, // запрос для агента лежит в params.source
    },
  },
  methods: { … },
});
```

| Поле шаблона | Что это |
| --- | --- |
| `component` | компонент вида — путь от папки плагина |
| `params` | JSON-схема `params` метрики: ей платформа проверяет и короткую форму, и полную с этим `component`. Значение с подстановкой `${{ … }}` схемой не проверяется — оно известно только объекту. Тип для компонента — `TemplateParams<typeof plugin, "list">` из `@mapward/plugin`: `MetricProps<TemplateParams<…>>` |
| `description` | что за вид — агенту |
| `agent` | запрос для агента: `{ method, params?, metric? }` — метод этого плагина (`metric` — имя аргумента, в который ляжет адрес самой метрики), или `{ param }` — запрос `{ plugin, method, params }` лежит в параметре метрики |

`set` метрики разворачивает короткую форму в `{ label, component, params, agent }` — пути
подстановкой от корня карты (`${{ mapward:// }}/_plugins/views/list.tsx`) — и отвечает тем, что
легло в файл. Встроенные: `views` — `list`, `tree`, `link`, `status`, `text`, `markdown`;
`objects-map` — `view` (холст, агенту — `view` с адресом метрики).

## Готовые виды `views`

Список, дерево, ссылка, статус, текст — компоненты встроенного плагина `views`. Метрика называет
вид своим `component`, а данные — в `params`:

```json
{
  "label": "Доки архитектуры",
  "component": "${{ mapward:// }}/_plugins/views/tree.tsx",
  "params": {
    "source": {
      "plugin": "${{ mapward:// }}/_plugins/files",
      "method": "tree",
      "params": { "path": "${{ mapward://@ }}/ru/docs/architecture", "git": true }
    },
    "empty": "доков нет"
  },
  "agent": {
    "plugin": "${{ mapward:// }}/_plugins/files",
    "method": "tree",
    "params": { "path": "${{ mapward://@ }}/ru/docs/architecture", "git": true }
  }
}
```

| Параметр | Что это |
| --- | --- |
| `source` | `{ plugin, method, params }` — метод, который даёт данные потоком; подписка живёт, пока вид на экране |
| `data` | статика вместо источника — рисуется с первого кадра |
| `empty` | что сказать, когда показывать нечего; у `agent.ask`, которого не спрашивали, — тоже |
| `refresh` | изменяющий метод источника для кнопки «обновить», с теми же параметрами (`refresh` у `agent.ask`). Не назван — кнопка переподписывается на источник; у статики кнопки нет |
| `collapsed` | метрика приходит свёрнутой |

`agent` метрики — тот же `source`, слово в слово: агент видит то же, что человек на экране.

Короче — шаблоном (`edit_map` → `set` метрики): `{ "label": "Доки архитектуры", "plugin":
"_plugins/views", "template": "tree", "params": { "source": …, "empty": "доков нет" } }`.
Платформа развернёт её в `component` и `agent` (агенту — тот же `source`) и проверит `params`
схемой вида.

**Пути плагинов** в `source` пишутся подстановкой от карты — `${{ mapward:// }}/_plugins/files` —
и после неё абсолютные. Так один текст годится и в `source`, и в `agent`, и в метрике прототипа,
которую наследник получает по `extends`: путь от `config.json` считался бы от чужой папки.
Платформа путь, начинающийся с подстановки, к папке слоя не привязывает.

Вид рисует рамку (`frame.tsx`): подпись, время ответа (если он старше 10 минут), «загружается…»,
ошибку — текстом или красной точкой у прежнего значения, кнопку обновления при наведении и
сворачивание. Что внутри — кирпич `Display` из `./bricks/` по виду; раскрытые папки дерева
помнятся у человека, свои на объект и метрику. Голый массив у `list` и `tree` и голая строка у `text` и
`markdown` — та же форма: так отвечают скрипты.

Источник отдаёт данные как есть — или обёрткой `{ asked, updatedAt?, data?, busy? }`, когда у
данных есть своё время: так отвечает `agent.ask`. Тогда время в рамке — время ответа, `busy` —
«спрашиваю», `asked: false` — `empty` или «не спрашивали».

## Встроенные плагины

Часть плагинов приходит с mapward — по модели shadcn: исходники лежат при инструменте и
копируются в карту один раз, в `_plugins/<имя>/`. Дальше это код проекта: его правят человек и
агент, как свой. Существующую копию mapward не перезаписывает никогда — ни установкой, ни
обновлением; правка переживает всё.

| Плагин | Что умеет |
| --- | --- |
| `files` | `tree({ path, include?, exclude?, content?, git? })` — дерево папки потоком `{ children }`, с вотчером; `git: true` — пометки `M A D U C` на узлах, папка берёт сильнейшую, и вотчер на индекс git. `summary` — сводка для агента. Открыть файл — `navigation` |
| `objects-map` | холст карты: `view({ view, config? })` — вьюха потоком, `edit({ view?, ops })` — правка операциями холста (карту правит платформа через `ctx.editMap`, `map-state.json` — плагин), `undo({ id })`, `redo({ id })` — отмена обоих; компонент `view.tsx` — метрика-холст. Сам холст — компоненты плагина (`canvas/`, на `@xyflow/react` из его `package.json`): правьте их, как свой код. См. [метрики](metrics.md#вьюха-objects-map) |
| `views` | готовые виды метрики: `list.tsx`, `tree.tsx`, `link.tsx`, `status.tsx`, `text.tsx`, `markdown.tsx` — и кирпичи, из которых они собраны, `bricks/`: их берут и свои компоненты карты. Методов нет. См. [виды](#готовые-виды-views) и [кирпичи](#кирпичи-views) |
| `navigation` | `open({ link, line? })`: `mapward://…` — объект карты, ответ `{ kind: "object", address }`, переходит зовущий; файл (абсолютный, от корня проекта или `mapward://@/…`) — в редакторе, папка — в проводнике редактора (`{ kind: "folder" }`); `http(s)://` — через `vscode.open`. Без редактора файл и адрес — ошибка. Им открывает ссылки `useNavigation()` компонентов |
| `screenshot` | `capture({ metric, width?, height?, base64?, viewState?, expand?, params? })` → `{ path, console, errors }`; `viewState` — значения `useViewState` по ключу, `expand: "all"` — всё раскрыто и ничего не свёрнуто, `params` — `params` метрики поверх конфига; все три — только на этот снимок, файлы карты и настройки человека не меняются: метрика так, как её видит человек, — та же сборка вебвью в безголовом Chromium, с консолью и ошибками страницы. См. [ниже](#скриншот-метрики) |
| `shell` | для экшона — `run({ command, cwd?, env?, input?, inputs?, timeout? })`, вывод строками по мере появления, отписка снимает процесс, и `steps({ steps, env?, inputs?, timeout? })` — шаги `script`/`prompt` по очереди, см. [экшоны](actions.md#встроенные-shell-и-agent). Для метрики — `json({ command, cwd?, env?, watch?, from?, timeout? })`: вывод — значение, разобранное json-ом |
| `agent` | для экшона — `run({ prompt, permissions?, cwd?, env?, inputs?, timeout? })`: `claude -p` с потоком событий, ход строками лога, ответ — итогом `{ answer }`. Для метрики — `ask({ prompt, shape?, cache, permissions? })` и `refresh` с теми же параметрами |

Поставить:

- `mapward plugin add <имя> [папка]` — в первую карту отсюда; папка — от корня карты, по
  умолчанию `_plugins/<имя>`;
- агенту — `add_plugin { name, path? }`;
- или ничего не делать: плагин по пути `<карта>/_plugins/<имя>` встроенного, которого ещё нет,
  платформа копирует сама на первое обращение.

Папка уже есть — отказ. Скопированное самим mapward доверено сразу: его код пришёл с
инструментом, и вопроса «Доверять?» о нём нет.

У встроенного плагина бывают свои зависимости — `dependencies` в его `package.json` (у
`objects-map` это `@xyflow/react` для холста). Их mapward ставит сразу после
копирования, в папку плагина: `npm install --omit=dev --omit=peer --no-package-lock`. Всегда
npm, а не менеджер проекта: папка плагина — не член рабочего пространства, pnpm внутри
pnpm-проекта ставил бы всё пространство, а npm кладёт плоский `node_modules` в саму папку — там
сборщик компонента его и ищет. React, `react-dom`, `rxjs` и `@mapward/component` отдаёт карта, поэтому
peer-зависимости не ставятся: своя копия React сломала бы хуки. `node_modules` закрыт
`.gitignore` плагина. Нет сети — копия остаётся, а установка отвечает отказом с командой, которую
выполнить потом самому; так же, если хост пакеты не ставит. Сборка компонента, не нашедшая
пакет, напоминает о том же.

## Скриншот метрики

`screenshot.capture({ metric: "mapward://…/_metrics/<ключ>", width?, height? })` рисует одну
метрику табом во всю ширину и снимает PNG во всю высоту. Снимок ложится файлом в
`.mapward/screenshots/` карты — файл на метрику, новый заменяет прошлый, — и в ответе `path`:
агент открывает его и смотрит. Строкой base64 (`png`) — только с `base64: true`. `console` —
строки консоли страницы, `errors` — её ошибки и `console.error`: по ним видно, почему компонент
нарисовался не так.

Снимает, когда страница готова: заглушек загрузки не осталось и разметка стихла. Заглушки
помечены `data-loading` — «Читаем карту…», «собирается…» у компонента, «загружается…» у видов
`views`; свой компонент помечает так же своё «грузится», чтобы скриншот его дождался. Не
дождался за 20 с — снимок как есть, а в `console` строка, что не догрузилось.

Перекрытия — только на этот снимок, ни файлы карты, ни настройки человека они не меняют:

- `viewState: { ключ: значение }` — значения `useViewState`: раскрытые папки дерева
  (`views:tree:<объект>#<метрика>`), свёрнутость рамки (`views:folded:<объект>#<метрика>`), масштаб
  холста. Запись состояния вида на странице снимка — только в её память.
- `expand: "all"` — всё раскрыто, ничего не свёрнуто. Что значит «раскрыто» для ключа, говорит
  тот, кто его читает: `useViewState(ключ, начальное, { expanded })`. У кирпичей `views` дерево
  отдаёт `"all"` (все папки), рамка — «не свёрнута»; свой компонент называет своё `expanded`.
  Ключ из `viewState` сильнее `expand`.
- `params: { … }` — `params` снимаемой метрики поверх её `config.json`, слиянием по ключу:
  `expand` холста `objects-map`, `maxHeight` и т.п.

Как устроено: плагин поднимает на петле маленький http-сервер со сборкой вебвью
(`ctx.webview.assets`) и прокладкой вместо `acquireVsCodeApi`, а сообщения клиента проксирует на
мост платформы (`ctx.webview.bridge`, рядом с MCP-сервером редактора). Страница та же, что в
вебвью, и платформа отвечает ей как вебвью: значения, сборки компонентов и вызовы плагинов —
настоящие.

Ограничения:

- рисует только платформа в редакторе: у `mapward mcp` без живого редактора клиента нет, и
  `capture` отвечает ошибкой. Редактор с картой открыт — `mapward mcp` сам ходит к нему (см.
  [mcp](mcp.md));
- тема — тёмная VS Code по умолчанию, а не тема человека: её цвета снаружи редактора не узнать;
- первый вызов ставит `playwright-core` в `~/.mapward/screenshot` (`MAPWARD_SCREENSHOT_CACHE` —
  другая папка) и Chromium в кэш Playwright. Нужны сеть и `npm`; без них — ошибка с тем, что
  поставить руками;
- «нарисовалось» — когда разметка стихла (0,7 с без изменений), но не дольше 20 с: метрика,
  которая всё время что-то меняет, снимается как есть, и в `console` об этом строка.

## Проверка плагина

После правки кода — одна команда: `mapward plugin check <путь> [карта]` (путь — от папки, где
команда запущена), агенту — `check_plugin { plugin }`. Ответ один и тот же: шаги со статусом и
строками.

1. Сборка — ошибки строками `файл:строка:колонка: что не так`.
2. Процесс и рукопожатие — поднялся ли, не упал ли `init`; с хвостом лога.
3. Самоописание — методы, читающий или изменяющий, и читаются ли их JSON-схемы.
4. Метрики карты, которые ссылаются на плагин (`agent.plugin` — он, или компонент лежит в его
   папке): компонент собирается, запрос для агента зовётся пробно — есть ли метод, проходят ли
   параметры его схему, отвечает ли он.

Кого компонент зовёт хуками, по коду не узнать — это видно только на экране (`screenshot`).

## Доверие

Плагин — код, который запускается на машине человека. Поэтому в первый раз, когда понадобился
плагин по новому пути, редактор спрашивает «Доверять?». Ответ хранится у человека,
`~/.mapward/trust.json`, а не в репозитории — чужой репозиторий не принесёт «доверено» с собой.
Доверие привязано к пути, а не к содержимому: правка агента вопроса не вызывает, `git pull` —
тоже. `mapward mcp` в консоли спросить не может и недоверенный плагин не запускает: ошибка
«плагин не доверен, подтвердите его в редакторе».

## Агенту

- `read_object` без `metrics` отдаёт перечень метрик без значений: значение бывает вызовом
  плагина, и без просьбы плагины не будятся. Значения — у метрик, названных в `metrics` или
  вкладкой в `group`; у метрики-компонента это ответ её запроса для агента.
- `describe_plugin { plugin }` — методы плагина, читающий или изменяющий, JSON-схемы. Плагина по
  пути нет — ошибка с перечнем встроенных.
- `add_plugin { name, path? }` — поставить встроенный плагин в карту; папка уже есть — отказ.
- `check_plugin { plugin, timeout? }` — проверить плагин после правки: сборка, процесс,
  самоописание и метрики, которые на него ссылаются.
- `call_plugin { plugin, method, args, wait }` — вызов метода; `wait: "complete"` ждёт конца потока.
  Изменяющие методы открыты агенту; отменить сделанное — забота плагина.

Путь плагина во всех — от корня карты или абсолютный.
