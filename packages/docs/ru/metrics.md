# Метрики

Метрика — папка в `_metrics/` с `config.json`. Конфиг описывает пайплайн: **коллекторы →
трансформы → дисплей**. Своих типов метрик в ядре нет, есть механизмы, из которых метрика
собирается.

```ts
type Metric = {
  label?: string
  extends?: string                                  // mapward:// адрес другой метрики
  refresh?: "manual" | "on-display" | `interval:${string}`   // default manual
  collectorsCache?: boolean
  collectorsStaleTime?: number                      // мс, сколько сбор считается свежим
  collectorsTimeout?: number                        // мс, сколько сбору позволено идти
  collectors?: MetricCollect[]
  transformsCache?: boolean
  transformsStaleTime?: number
  transformsTimeout?: number
  transforms?: MetricTransform[]
  display?: MetricDisplay
  collapsed?: boolean
}
```

Всё поля опциональны: любое может приехать от прототипа или от родительской метрики. Сначала
резолвится `extends` самой метрики, потом `extends` объектов — рекурсивно, цикл ошибка.

## Когда метрика считается

- `manual` — ждёт кнопки. Умолчание;
- `on-display` — собирается при открытии объекта; удобно для быстрого, чтобы не держать кэш;
- `interval:<мс>` — тикает, пока объект открыт хотя бы в одном виде. Карта закрыта — метрика
  не считается: фоновых прогонов за спиной у человека нет.

Всё, что поднимает агента, живёт на `manual`: это время и деньги, и на каждую отрисовку так
делать нельзя. Исключение ставят руками — [`watch`](#вотчер-шага) у шага работает и на `manual`.

Значение при этом показывается сразу — то, что лежит в кэше, — а прогон идёт следом и меняет
его. Лоадер остаётся для случая, когда показывать нечего. Пока результат свежий по
`collectorsStaleTime` или `transformsStaleTime`, открытие объекта прогон не запускает вовсе;
свежесть считается по стадиям, поэтому свежий сбор с протухшим трансформом означает прогон
одного трансформа. Кнопка обновления свежесть не спрашивает.

Своего срока у метрики может и не быть — тогда берётся тот, что задан на карту в
[`mapward.json`](config.md). Метрика его перебивает: общее здесь умолчание, а не замена. Не
задано ни там, ни там — метрика пересобирается при каждом открытии.

Стадия, которой задан `collectorsTimeout` или `transformsTimeout`, дольше этого не идёт:
время вышло — прогон снимается, метрика краснеет, причина уходит в логи, прежнее значение
остаётся. От отмены это отличается тем, что отмене записать нечего, а здесь ответ обещали и
не дали. Зовущий может назвать свой предел и перебить метрикин — так делает MCP.

Значения живут в сторе сервера, одном на карту, и виды его читают: сайдбар и табы одного окна
показывают одно и то же, включая идущий прогон.

## Коллекторы

Берут данные откуда угодно и отдают дальше.

| Вид | Что делает |
| --- | --- |
| `static` | значение прямо из конфига |
| `script` | команда оболочки; cwd — корень карты |
| `prompt` | агент в headless-режиме |
| `read-dir` | дерево файлов по `basePath`, с `include`/`exclude` и флагом `content` |
| `objects-map` | вьюха: объекты карты для дисплея `map` — см. [вьюха](#вьюха-objects-map) |

Коллекторов может быть несколько — тогда каждому нужен `name`, под которым результат ляжет
в общий объект.

Скрипт получает объект через окружение — `MAPWARD_OBJECT_PATH`, `MAPWARD_MAP_PATH`,
`MAPWARD_OBJECT_NAME`, `MAPWARD_OBJECT`: подстановка внутрь тела скрипта не дотягивается.

### Вьюха `objects-map`

Холст карты — метрика с коллектором `objects-map` и дисплеем `map`. Корня у вьюхи нет: на холсте
только то, что конфиг называет явно, плюс ссылки, добавленные на самом холсте. Вьюх у объекта
сколько угодно — «контейнеры», «сервисы и связи», «event storming», — и править карту можно на
любой из них.

```json
{
  "kind": "objects-map",
  "show": ["systems/*"],
  "prototypes": ["Сервис"],
  "exclude": ["systems/legacy/**"],
  "expand": { "objects": ["systems/shop"], "prototypes": ["mapward://prototypes/system"] },
  "style": {
    "all": { "shape": "rect", "view": "simple" },
    "prototypes": { "mapward://prototypes/service": { "shape": "round", "color": "#2a7" } },
    "objects": { "systems/shop/cart": { "view": "preview", "group": "превью", "width": 280 } }
  },
  "palette": {
    "objects": ["mapward://prototypes/service"],
    "relations": ["mapward://prototypes/calls"]
  },
  "placeObjects": "mapward://systems",
  "placeRelations": "mapward://relations"
}
```

- `show` — адреса и маски: `systems/*` — дети полки, но не их дети, `systems/**` — вся ветка,
  `mapward://…` — адрес как есть. `prototypes` добирает объекты этих прототипов по всей карте —
  адресом прототипа или его именем. `exclude` вырезает ветку целиком;
- полка — папка без `_index.json` — на холст не встаёт никогда, её дети поднимаются уровнем
  выше. Объект со связью (`from`/`to` в `props`) — не узел, а стрелка;
- `expand` — что рисуется **группой**, с жильцами внутри, поимённо и по прототипам; остальное
  встаёт одним узлом. Жильцы группы — её дети по папкам;
- `style` — как нарисовать узел: форма (`rect`, `round`, `ellipse`, `diamond`, `note`), цвет,
  поле `props`, которое идёт подписью (`label`), и вид — `simple`, фигура с подписью, или
  `preview`, полное [превью](#карточка-объекта) объекта с `group`, `width`, `maxHeight`. Три
  уровня — для всех, для прототипа, для объекта; побеждает самый узкий, поле за полем;
- `palette` — прототипы объектов и связей, которые боковая панель ставит на этой вьюхе;
- `placeObjects` — куда уходит объект, брошенный на пустое место; брошенный на группу становится
  её ребёнком. Не назван — создавать на пустом месте нельзя, и холст так и говорит.
  `placeRelations` — объект или полка, куда кладутся новые связи; не назван — стрелку не
  провести.

Что меняется на холсте, лежит в `map-state.json` рядом с `config.json` метрики, в папке объекта
(у метрики от прототипа — у наследника: состояние не наследуется):

```json
{
  "positions": { "mapward://systems/shop": { "x": 0, "y": 0 } },
  "expanded": { "mapward://systems/bank": false },
  "refs": ["mapward://partners/bank"],
  "shapes": [
    { "id": "s1", "kind": "text", "x": 40, "y": -80, "text": "зона оплаты", "fontSize": 18 },
    { "id": "s2", "kind": "line", "x": 0, "y": 0, "arrow": "end",
      "from": { "node": "mapward://systems/shop" }, "to": { "x": 300, "y": 40 } }
  ]
}
```

Позиция узла внутри группы — относительно группы. `expanded` — свёрнутое и развёрнутое руками
поверх `expand`. `refs` — ссылки на объекты, которые вьюха сама не выбирает: удалить ссылку не
значит удалить объект. `shapes` — фигуры, пометки на холсте без папки и метрик: `rect`, `ellipse`, `text` и `line`.
У фигуры есть `width` и `height`, заливка `color`, обводка `stroke`, `textColor` и `fontSize`. У
линии два конца, `from` и `to`, — точка `{ x, y }` или `{ node }`, узел или другая фигура, за
которыми конец едет; `arrow` — `none`, `end` или `both`. Линия — пометка, а не связь: связь
ставится стрелкой из палитры и заводит объект. Пишется файл
операциями правки, а не руками: холст и агент через [MCP](mcp.md) зовут одни и те же операции.

Свёртку, стрелки и вид считает коллектор, холст получает готовую картинку. Стрелка к жильцу
свёрнутой группы поднимается к самой группе, как в C4; несколько стрелок на одну пару узлов
склеиваются в одну с числом и списком связей; стрелка, у которой конец не попал на холст, не
рисуется.

Следит вьюха за картой сама, без поля `watch`: правка любого `_index.json` или `map-state.json`
карты пересобирает её, пока объект открыт.

## Трансформы

Коллектор отдаёт то, что есть на источнике, дисплей ждёт свою форму. Трансформ приводит одно
к другому и не обязателен: если коллектор уже отдал нужное, пайплайн идёт мимо.

- `script` — когда формат стабильный. Мгновенно и бесплатно;
- `prompt` — когда формат плавает. Парсить регуляркой вывод тестраннера хрупко, он меняется
  с версией; промпт переживает. Текст чаще всего не нужен: форму знает дисплей, и она уезжает
  в промпт сама;
- встроенный — тело лежит в самом инструменте, конфиг называет его именем и ничего не описывает
  командой.

Идут по порядку, вход в stdin, выход из stdout, выход одного — вход следующего.

### Встроенные шаги

Заводятся ради того, чего `script` не умеет: своего состояния. Вотчер есть у любого шага — полем
[`watch`](#вотчер-шага), — но скрипт следит за теми файлами, которые ему назвали, а встроенный шаг
сам знает, от чего устаревает его ответ, и будит метрику сам.

| Имя | Что делает |
| --- | --- |
| `git-status` | ставит узлам с файловой ссылкой пометку git: `M`, `A`, `D`, `U`, `C` |

```json
{ "transforms": [{ "kind": "git-status" }], "display": { "kind": "tree" } }
```

Ставится к любому коллектору: шаг смотрит на форму дисплея, а не на источник, — файловое дерево,
список требований, одиночная ссылка и вьюха карты размечаются одинаково. Ссылка на объект
(`mapward://`) и наружу (`https://`) пометки не получают — за ними не файл.

Папка берёт сильнейшую пометку потомков: `C`, потом `D`, `A`, `M`, `U`. Иначе свёрнутое дерево
прячет ровно то, ради чего на него смотрят.

Стадии трансформа со встроенным шагом свежесть не считается: `transformsStaleTime` удержал бы на
экране пометку вчерашнего дня. Вотчер шага следит за `.git/index` и `.git/HEAD` и запускает один
трансформ на уже собранных данных — коллекторы при этом не трогаются, и метрика, которую собирает
агент, от правки в репозитории не просыпается.

Упавший git метрику не роняет: данные идут дальше без пометок, причина уходит в
`transform.logs.json`. Не сошлась пометка, а не данные.

`transformsCache` при этом работает как обычно — то есть пометки лягут в `transform.json` и дадут
дифф в репозитории на каждый взгляд на карту. Комбинация шумная; тот, кто её поставит, выключит
кэш сам, а молча подменять настройку хуже.

## Вотчер шага

У любого коллектора и трансформа — `script`, `prompt`, `read-dir`, встроенного — может быть поле
`watch`. Изменение файла под ним перезапускает этот шаг, пока объект открыт:

```json
"watch": { "include": ["src/**/*.ts"], "exclude": ["**/*.test.ts"], "debounce": 300 }
```

- `include` — за чем следить. Пути считаются от той же папки, от которой шаг читает свои: у
  `read-dir` это `basePath`, у остальных — корень карты. Абсолютный путь остаётся как есть, так
  следят за кодом проекта вне карты; подстановки `${{ … }}` работают, как во всём конфиге;
- `exclude` — что из этого не в счёт, необязателен;
- `debounce` — сколько мс тишины ждать после последнего изменения. Без него берётся
  `watchDebounce` из [`mapward.json`](config.md), без того — 300 мс.

`read-dir` свои пути знает, поэтому ему хватает `"watch": true` или `"watch": { "debounce": 500 }`:
следим за его `basePath`, `include` и `exclude`. Явный `include` перебивает их. Остальным шагам
`include` нужен обязательно; без него вотчер не встаёт, а причина уходит в `collect.logs.json`.

**Написанный `watch` — это согласие на запуск.** Вотчер ставится при любом `refresh`, в том числе
`manual`, и у `prompt` тоже: агент на каждое сохранение — это деньги, но их тратит тот, кто
поставил поле.

Что перезапускается:

- вотчер **коллектора** — только этот коллектор. Остальные отдают свою часть из прошлого сбора:
  при нескольких коллекторах она лежит под их `name`, при одном это весь результат. Дальше, как
  обычно, идут все трансформы. Прошлого сбора нет — собираются все;
- вотчер **трансформа** — только трансформы на уже собранных данных.

Идущий прогон вотчер не ждёт и второго не заводит, а перезапускает свою часть внутри него:
идущий коллектор снимается и начинается заново, соседи продолжают, стадия ждёт всех. Сработал
вотчер коллектора, пока идут трансформы, — трансформы снимаются, коллектор собирается заново, и
трансформы идут ещё раз. Снятое вотчером — не неудача: в истории остаётся один прогон, с
источником «вотчер». Дебаунс срабатывает раньше отмены, поэтому пока файлы сохраняются подряд,
идущий шаг не трогается. Таймаут стадии считается от её начала, перезапуски его не продлевают.

Конфиг метрики живой: правка `watch` в `config.json` переставляет вотчер сразу, открывать объект
заново не нужно.

### Свежесть и вотчер

Поле `watch` на свежесть не влияет. Пока объект закрыт, вотчер не работает, и если с прошлого
сбора прошло меньше `collectorsStaleTime`, при открытии покажется кэш — даже если файлы за это
время менялись. Нужно «при открытии собирать заново, а дальше следит вотчер» — обнулите срок
явно:

```json
{
  "refresh": "on-display",
  "collectorsStaleTime": 0,
  "collectors": [{ "kind": "read-dir", "basePath": "src", "watch": true }]
}
```

Именно явно: без поля действует срок, заданный на всю карту. С трансформом с `watch` так же —
`transformsStaleTime: 0`. Исключение у `git-status` своё и остаётся как было: его пометки
пересчитываются при каждом открытии без оглядки на срок.

## Дисплеи

У каждого своя форма данных; пришло не то — метрика показывает ошибку валидации, а карта
продолжает работать.

| Дисплей | Форма |
| --- | --- |
| `text` | `{ text }` |
| `markdown` | `{ text }`, где текст — разметка |
| `link` | `{ label?, link? }` |
| `status` | `{ ok, summary? }` |
| `list` | `{ items: ListNode[] }` |
| `tree` | `{ children: TreeNode[] }` |
| `map` | `{ view, nodes, relations, shapes, palette, … }` — собирает [`objects-map`](#вьюха-objects-map) |
| `object` | `{ object, group?, width?, maxHeight? }` — [карточка объекта](#карточка-объекта) |
| `component` | своя, по `schema` — см. [свой компонент](#свой-компонент) |

У элемента списка и дерева кроме `label` и `link` есть `status` — `fail`, `success`,
`pending`, `idle` со своими цветами, плюс свой `color` и подпись `hint` в тултипе. У элемента
списка есть ещё `description` — вторая строка, приглушённая: проверке мало сказать, что что-то
не так, надо сказать, в чём именно.

`markdown` берёт ту же форму, что `text`: чтобы показать вывод по-человечески, метрике
достаточно поменять `display.kind`, не трогая коллекторы. Разбирается подмножество, названное
списком: заголовки, абзацы, списки с вложенностью по отступу, цитаты, блоки кода, черта, а
в строке — `код`, `[ссылка](куда)`, `**жирный**` и `*курсив*`. Таблиц, картинок и html нет.
Тем же разбором, но без блоков, рисуется `description` у элемента списка и узла дерева.

`link` — адрес карты, и по схеме понятно, как его открыть: `mapward://` ведёт на объект
карты, `https://` наружу, остальное — файл в проекте. Объект карточкой, а не ссылкой, рисуется
полем `object` — ниже.

Пустой результат — это ответ, а не отсутствие ответа: у дисплея есть `empty` — что сказать,
когда показывать нечего. «Не проверялось» у ручной проверки, «всё сделано» у пустой очереди.

`collapsed` сворачивает метрику по умолчанию. Свёрнутость, переключённая руками, живёт
в состоянии редактора и умолчание перекрывает: это удобство человека, репозиторию оно не видно.

### Карточка объекта

Превью объекта там, где он встречается на чужом экране: имя с прототипом (клик открывает
объект, ctrl + клик — табом), кнопки терминала, экшонов и директив этого объекта и метрики его
вкладки превью. Своего описания у превью нет — это одна из [вкладок](index-format.md#превью-объекта)
объекта, та, у которой `defaultPreview`, или названная явно.

Отдельного дисплея под списки карточек нет. Карточку рисует пункт с полем `object`:

```json
{ "object": "mapward://packages/core", "group": "превью", "width": 280, "maxHeight": "240px" }
```

- у `list` и `tree` такой пункт встаёт карточкой вместо строки; `label`, `link`, статус и экшон
  строки у него не рисуются — имя, ссылка и экшоны у карточки свои. Дети узла дерева
  раскрываются под карточкой, строки и карточки в одном списке смешиваются;
- у `map` узел рисуется так, как решил конфиг вьюхи: с видом `preview` — карточкой, с `simple` —
  фигурой с подписью, а карточка открывается по клику;
- дисплей `object` — одиночный объект: значение — тот же пункт, метрика встаёт в клетку сетки
  по ключу, как любая, и наследуется от прототипа. Так в одной сетке стоят несколько объектов,
  каждый своей вкладкой.

`group` не назван — берётся вкладка с `defaultPreview`, нет и её — у карточки одна шапка.
Названной вкладки у объекта нет — карточка так и говорит, «нет вкладки …», а не подставляет
другую: чужие метрики под видом заказанных хуже пустого места. Объекта по адресу нет — «нет
объекта …».

Размер — свойство места, где карточка нарисована, а не объекта: `width` и `maxHeight`, как в
раскладках — css-строка, число значит пиксели. Без `maxHeight` карточка растёт по содержимому,
с ним шапка стоит, а метрики под ней прокручиваются целиком. Ширины нет — в списке и дереве
карточка во всю ширину, в клетке сетки — во всю клетку, на карте — ширина по умолчанию, чтобы
узлы не наезжали друг на друга.

Карточка подписана на метрики своей вкладки, пока её видно: ушла с экрана — подписка гаснет
вместе с вложенными в неё карточками. На карте детей холст рисует только видимые узлы, поэтому
цена карты — то, что на экране. Вложенность не ограничена: внутри карточки снова бывают
карточки, и круг из ссылок на себя — ответственность карты, а не инструмента.

### Свой компонент

Когда готовых форм мало, метрика рисуется своим React-компонентом: `.tsx` рядом с её
`config.json`.

```json
{
  "display": {
    "kind": "component",
    "component": "./display.tsx",
    "schema": "./schema.json"
  }
}
```

`component` — путь к компоненту, `schema` — JSON-схема данных, объектом прямо здесь или путём к
`.json`. Пути считаются от папки того `config.json`, где написаны: компонент прототипа лежит у
прототипа, и наследник с одной строкой `extends` находит его сам.

Схема и проверяет данные, и подсказывает агенту. Не прошли — метрика красная, в ячейке путь до
поля и что ожидалось; в `read_object` то же лежит в `value.invalid`. Агенту-коллектору и
агенту-трансформу схема уходит в промпт вместо формы готового дисплея. Без схемы данные идут
компоненту как есть.

Компонент экспортирует по умолчанию функцию от пропсов:

```tsx
import type { DisplayProps } from "@mapward/display";
import { List } from "@mapward/display";
import type { Data } from "./display.data";

export default function Display({ data, open }: DisplayProps<Data>) {
  const todo = data.items.filter((item) => !item.done);
  return (
    <div className="flex flex-col gap-1">
      <span className="text-[var(--mw-descriptionForeground)]">осталось {todo.length}</span>
      <List items={todo.map((item) => ({ label: item.title, link: item.file }))} />
      <button onClick={() => open("mapward://videos")}>все записи</button>
    </div>
  );
}
```

| Пропс | Что это |
| --- | --- |
| `data` | значение метрики, уже проверенное схемой |
| `object` | `address`, `name`, `path`, `props` объекта |
| `metric` | `key`, `address`, `label`, `updatedAt`, `ok`, `busy` |
| `open(link)` | открыть ссылку, как любую ссылку карты: файл, `mapward://`, `https://` |

Из `@mapward/display` приходят кусочки, которыми нарисована сама карта: `Link`, `Markdown`,
`StatusDot`, `List`, `FileTree`. Их пункты — те же, что у `list` и `tree`. Раскрытые папки
`FileTree` карта запоминает сама, как и у готового `tree`: у человека, на объект и метрику.
Деревьев в компоненте несколько — дайте каждому свой `id`, иначе они раскрываются заодно. `react` и
`@mapward/display` отдаёт карта, в сборку они не кладутся: две копии React на странице ломают
хуки.

Остальное импортируется как обычно: свои файлы по относительному пути, пакеты — из
`node_modules`. Пакет ищется от папки компонента вверх до первого `node_modules`, где он есть, а
не нашёлся — в `node_modules` корня проекта. Собирает всё это сервер карты, esbuild в
WebAssembly, так что ставить в проект сборщик не нужно. Правка компонента или любого его файла
вне `node_modules` пересобирает дисплей сразу. Не собралось — в ячейке ошибки с файлом и
строкой. Упал при отрисовке — красная строка в ячейке, соседние метрики живут.

Классы — tailwind, любые, включая произвольные значения: `grid-cols-[2fr_1fr]`. Css пишется
на классы, найденные в файлах компонента, без сброса стилей, в тех же слоях, что у карты. Цвета
берутся у темы редактора, как у всей карты: `text-[var(--mw-foreground)]`,
`bg-[var(--mw-editor-background)]`. Своей темы у компонента нет. Css, импортированный из
компонента, едет вместе с этим.

Типы — пакетом `@mapward/display`: его ставят в проект dev-зависимостью вместе с
`@types/react`. Проверяет компонент команда:

```
mapward display check mapward://videos/_metrics/transcripts
```

Она пишет рядом с компонентом `display.data.d.ts` с `export type Data` по схеме, гоняет
TypeScript проекта по компоненту, собирает его так же, как карта, и сверяет со схемой последнее
собранное значение. Ошибки — строками с файлом и позицией. Агенту её хватает после каждой
правки: TypeScript в карту не встроен, на сохранении типы не проверяются.

## Кэши и логи

Рядом с `config.json` ложатся `collect.json` и `transform.json` — если метрика их попросила
флагами `collectorsCache` и `transformsCache`. Лежат они всегда у объекта: конфиг метрика
наследует от прототипа, а кэш у каждого наследника свой — определения наследуются, состояние
нет. Быстрому скрипту кэш не нужен, а диффы в
репозитории от него будут при каждом взгляде на карту. Результат промпта, наоборот, дорогой
и невоспроизводимый — его кэш коммитится.

Дисплей берёт данные из памяти, если прогон уже был; иначе из `transform.json`; иначе из
`collect.json`.

`updatedAt` пишет рантайм рядом с данными, и по нему видно, когда метрику собирали. Там же
`ok` — как прошёл прогон; это не тот `ok`, что внутри данных у дисплея `status`: тот про
тесты, этот про то, отработал ли коллектор.

```json
{ "updatedAt": "2026-08-28T04:10:00Z", "ok": true, "data": { "ok": true, "summary": "12 passed" } }
```

**При неуспехе данные не затираются.** Пишется `ok: false` и новый `updatedAt`, `data`
остаётся от прошлого удачного раза: значение было верным, обновить его не смогли, и это
честнее пустоты.

Скрипты и промпты по дороге пишут в stderr, и когда прогон упал, это единственное, что
объясняет почему. Логи лежат отдельно — `collect.logs.json` и `transform.logs.json`: упасть
шаги могут по отдельности, и человеку нужно попасть в лог сломавшегося.

## Прогоны

Каждый прогон метрики, кроме пометки git от вотчера, записывается: когда, откуда запущен
(кнопка, агент, само открытие объекта), шаги — сбор и трансформ — с логом каждого и итог. Это
та же история, что у [экшонов](actions.md), и лежит она там же — в `.mapward/runs/` карты, в git
не попадая.

Удачный прогон на метрике ничем не отмечен: зелёная точка на каждой метрике шумела бы, а
сказать ей нечего. Остаётся красная — и ведёт на последний прогон метрики, туда, где написано,
почему он не удался.
