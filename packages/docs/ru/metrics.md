# Метрики

Метрика — папка в `_metrics/` с `config.json`. Метрика — это компонент: `.tsx`, который сам
берёт данные у [плагинов](plugins.md) и сам их рисует. Своего конвейера сбора у платформы нет:
что собрать, когда и как показать, решают компонент и плагины, которых он зовёт.

```ts
type Metric = {
  label?: string
  extends?: string                         // mapward:// адрес другой метрики
  component: string                        // .tsx: от этого config.json или подстановкой
  params?: Record<string, unknown>         // настройки компонента; приходят ему пропсом
  agent?: { plugin: string; method: string; params?: unknown }   // что видит агент
}
```

Любое поле может приехать от прототипа или от общей метрики по `extends`: сначала резолвится
`extends` самой метрики, потом `extends` объектов — рекурсивно, цикл ошибка. Слои ложатся друг
на друга целиком, кроме `params` — они сливаются по имени: наследник, который только свернул
метрику (`{ "params": { "collapsed": true } }`), не теряет её источник.

Подстановки `${{ … }}` разрешаются во всём конфиге по объекту, на котором метрика стоит, — так
общая метрика берёт пути и имена у наследника. Путь `component` и `agent.plugin` считается от
папки того `config.json`, где он написан; путь, который начинается подстановкой
(`${{ mapward:// }}/_plugins/views/list.tsx`), абсолютный после неё и годится в любом слое.

`agent` — то, что агент видит вместо экрана: метод плагина с параметрами. Компонент агент не
исполняет, поэтому без запроса ему остаются только методы плагина.

## Готовые виды и откуда данные

Чаще всего метрике хватает готового вида — компонента встроенного плагина `views`: `list.tsx`,
`tree.tsx`, `link.tsx`, `status.tsx`, `text.tsx`, `markdown.tsx`. Данные виду называют в
`params`: `source` — метод плагина, который даёт их потоком, или `data` — статика. Вид рисует
рамку — подпись, время ответа, «загружается…», ошибку, кнопку обновления, сворачивание, — а
внутри кирпич `Display` из своих `bricks/` по своей форме. Параметры видов — в [плагинах](plugins.md#готовые-виды-views).

```json
{
  "label": "Версия",
  "component": "${{ mapward:// }}/_plugins/views/text.tsx",
  "params": {
    "source": {
      "plugin": "${{ mapward:// }}/_plugins/shell",
      "method": "json",
      "params": {
        "command": "node -p \"JSON.stringify({ text: require('./package.json').version })\"",
        "cwd": "${{ mapward://~#props.fullPath }}",
        "watch": { "include": ["${{ mapward://~#props.fullPath }}/package.json"] }
      }
    }
  },
  "agent": {
    "plugin": "${{ mapward:// }}/_plugins/shell",
    "method": "json",
    "params": {
      "command": "node -p \"JSON.stringify({ text: require('./package.json').version })\"",
      "cwd": "${{ mapward://~#props.fullPath }}",
      "watch": { "include": ["${{ mapward://~#props.fullPath }}/package.json"] }
    }
  }
}
```

`agent` — тот же `source`, слово в слово: агент видит то же, что человек. Пути плагинов пишутся
от карты подстановкой — `${{ mapward:// }}/_plugins/<имя>`: один текст и в `source`, и в
`agent`, и в метрике прототипа у любого наследника.

Источники данных — встроенные плагины:

| Метод | Что даёт |
| --- | --- |
| `shell.json({ command, cwd?, env?, watch?, from? })` | вывод команды, разобранный json-ом; не json — `{ text }` |
| `files.tree({ path, include?, exclude?, content?, git? })` | дерево папки `{ children }` потоком, с вотчером |
| `agent.ask({ prompt, shape?, cache, permissions? })` | сохранённый ответ агента; новый — кнопкой, методом `refresh` |
| `data` в `params` вида | статика прямо в конфиге |

### Команда: `shell.json`

Команда идёт оболочкой из папки карты (`cwd` — другая папка), вывод разбирается json-ом, а не
json — становится `{ text }`, чтобы его хотя бы показал вид `text`. Ненулевой код — ошибка с
хвостом stderr. Значение одно на подписку: каждый показ метрики — новый запуск.

Объект команде называют подстановками: в её аргументы или в `env` —
`"env": { "MAPWARD_OBJECT_PATH": "${{ mapward://~ }}", "MAPWARD_MAP_PATH": "${{ mapward:// }}" }`.
Сам плагин не знает, на каком объекте стоит метрика.

`watch` перезапускает команду по изменению файлов, пока метрика на экране:

```json
"watch": { "include": ["src/**/*.ts"], "exclude": ["**/*.test.ts"], "debounce": 300 }
```

Глобы — абсолютные или от `cwd`; `debounce` — сколько мс тишины ждать после последнего
изменения, по умолчанию 300. Нет папки — за ней не следят, команда идёт как шла.

`from` — вход команды: другой метод потоком, `{ plugin, method, params }`. Каждое его значение
уходит в stdin команды JSON-ом, и команда запускается заново. Так скрипт превращает дерево файлов
в дерево требований и пересчитывает его на каждое изменение файлов:

```json
{
  "command": "node \"${{ mapward://prototypes/system }}/_metrics/requirements/status.mjs\"",
  "from": {
    "plugin": "${{ mapward:// }}/_plugins/files",
    "method": "tree",
    "params": { "path": "${{ mapward://@ }}/ru/requirements", "include": ["**/*.md"], "content": true, "git": true }
  }
}
```

### Файлы: `files.tree`

Дерево папки `{ children: [{ label, link, isDir, children, text?, git? }] }`: папки сверху,
дальше по имени. `include` и `exclude` — глобы от `path`; с `include` папка, в которой ничего
подходящего нет, не показывается. `content: true` кладёт в узел текст файла. `.git` не
читается никогда.

Дерево одно на всех подписчиков с теми же параметрами и живёт, пока на него кто-то смотрит:
десять открытых пакетов с одной папкой — один вотчер. Изменение файла перечитывает дерево.

`git: true` ставит узлам пометку git — `M`, `A`, `D`, `U`, `C` — и следит ещё и за индексом и
`HEAD` репозитория: пометка протухает не по часам, а по `git add`, коммиту и смене ветки. Папка
берёт сильнейшую пометку потомков — `C`, потом `D`, `A`, `M`, `U`, — иначе свёрнутое дерево
прячет ровно то, ради чего на него смотрят. Упавший git дерево не роняет: узлы идут без
пометок.

### Агент: `agent.ask`

Спрашивать агента — время и деньги, поэтому `ask` агента не спрашивает: первым значением он
отдаёт сохранённый ответ из файла `cache`. Новый ответ даёт только изменяющий метод `refresh` с
теми же параметрами — кнопка обновления вида (`"refresh": "refresh"` в `params`), `call_plugin`
агента или `mapward metric`. Пока идёт вопрос, все, кто смотрит, видят «спрашиваю»; ответ
приходит им сам.

```json
{
  "label": "Расхождения с архитектурой",
  "component": "${{ mapward:// }}/_plugins/views/list.tsx",
  "params": {
    "source": {
      "plugin": "${{ mapward:// }}/_plugins/agent",
      "method": "ask",
      "params": {
        "prompt": "Док об устройстве — …, код — ${{ mapward://~#props.fullPath }}. …",
        "shape": "list",
        "cache": "${{ mapward://~ }}/_metrics/architecture-drift/answer.json"
      }
    },
    "empty": "не проверялось",
    "refresh": "refresh"
  },
  "agent": { "…": "тот же source" }
}
```

- `prompt` — что спросить. Объект в промпт сам не попадает: его называют подстановками;
- `shape` — форма ответа: имя вида (`list`, `tree`, `link`, `status`, `text`, `markdown`) или
  JSON-схема. Подсказка уходит в конец промпта, чтобы агент не угадывал;
- `cache` — файл ответа. Он лежит у объекта, даже когда конфиг пришёл от прототипа: определения
  наследуются, состояние нет. Ответ дорогой и невоспроизводимый — файл коммитится, и ответ видят
  все, кто открыл карту;
- `permissions` — что агенту можно, как у экшона: метрике, которая гоняет линтер, нужен
  `["Bash(pnpm oxlint:*)"]`. Без поля агент только читает.

Ответ разбирается json-ом — первый объект или массив, который читается, в том числе внутри
```` ```json ````; не json — `{ text }`. В файле — когда спросили и что ответил:

```json
{ "updatedAt": "2026-10-29T04:10:00Z", "data": { "ok": true, "summary": "12 passed" } }
```

Значение `ask` — `{ asked, updatedAt?, data?, busy? }`: `asked: false` — агента не спрашивали ни
разу, вид говорит `empty` или «не спрашивали». **Неудача ответ не стирает**: вопрос упал или его
сняли — файл остаётся прежним, а ошибка — у кнопки.

## Вьюха `objects-map`

Холст карты — метрика-компонент встроенного плагина `objects-map`: вид — `view.tsx` плагина, а
что показать, сказано в её `params`. Корня у вьюхи нет: на
холсте только то, что `params` называют явно, плюс ссылки, добавленные на самом холсте. Вьюх у
объекта сколько угодно — «контейнеры», «сервисы и связи», «event storming», — и править карту
можно на любой из них. Плагин ставится в карту один раз (`_plugins/objects-map`), а встроенный,
которого там ещё нет, доставляется сам на первый вызов.

```json
{
  "label": "Холст",
  "component": "../../_plugins/objects-map/view.tsx",
  "params": { "show": ["systems/*"], "placeObjects": "mapward://systems" },
  "agent": {
    "plugin": "../../_plugins/objects-map",
    "method": "view",
    "params": { "view": "mapward://_metrics/canvas" }
  }
}
```

`params` целиком:

```json
{
  "show": ["systems/*"],
  "prototypes": ["Сервис"],
  "exclude": ["systems/legacy/**"],
  "expand": { "objects": ["systems/shop"], "prototypes": ["mapward://prototypes/system"] },
  "style": {
    "all": { "shape": "rect", "view": "simple" },
    "prototypes": { "mapward://prototypes/service": { "shape": "round", "color": "#2a7" } },
    "objects": { "systems/shop/cart": { "view": "preview", "group": "превью", "width": 280 } }
  },
  "palette": {
    "objects": ["mapward://prototypes/service"],
    "relations": ["mapward://prototypes/calls"]
  },
  "placeObjects": "mapward://systems",
  "placeRelations": "mapward://relations"
}
```

- `show` — адреса и маски: `systems/*` — дети полки, но не их дети, `systems/**` — вся ветка,
  `mapward://…` — адрес как есть. `prototypes` добирает объекты этих прототипов по всей карте —
  адресом прототипа или его именем. `exclude` вырезает ветку целиком;
- полка — папка без `_index.json` — на холст не встаёт никогда, её дети поднимаются уровнем
  выше. Объект со связью (`from`/`to` в `props`) — не узел, а стрелка;
- `expand` — что рисуется **группой**, с жильцами внутри, поимённо и по прототипам; остальное
  встаёт одним узлом. Жильцы группы — её дети по папкам;
- `style` — как нарисовать узел: форма (`rect`, `round`, `ellipse`, `diamond`, `note`), цвет,
  поле `props`, которое идёт подписью (`label`), и вид — `simple`, фигура с подписью, или
  `preview`, полное [превью](#карточка-объекта) объекта с `group`, `width`, `maxHeight`;
  `align` — выравнивание подписи простой карточки: `left`, `center` (умолчание), `right`. Три
  уровня — для всех, для прототипа, для объекта; побеждает самый узкий, поле за полем. Стиль
  прототипа связи рисует её стрелку: `color` и линия `line` — `solid`, `dashed` или `dotted`.
  Прототип связи из палитры без своей `line` получает узор по месту в палитре — две связи
  палитры не выглядят одинаково и без стиля;
- `palette` — прототипы объектов и связей, которые боковая панель ставит на этой вьюхе;
- `placeObjects` — куда уходит объект, брошенный на пустое место; брошенный на группу становится
  её ребёнком. Не назван — создавать на пустом месте нельзя, и холст так и говорит.
  `placeRelations` — объект или полка, куда кладутся новые связи; не назван — стрелку не
  провести.

Что меняется на холсте, лежит в `map-state.json` рядом с `config.json` метрики, в папке объекта
(у метрики от прототипа — у наследника: состояние не наследуется):

```json
{
  "positions": { "mapward://systems/shop": { "x": 0, "y": 0 } },
  "refs": ["mapward://partners/bank"],
  "copies": { "mapward://partners/bank#2": { "object": "mapward://partners/bank" } },
  "ends": { "mapward://relations/shop-to-bank": { "to": "mapward://partners/bank#2" } },
  "shapes": [
    { "id": "s1", "kind": "text", "x": 40, "y": -80, "text": "зона оплаты", "fontSize": 18 },
    { "id": "s2", "kind": "line", "x": 0, "y": 0, "arrow": "end",
      "from": { "node": "mapward://systems/shop" }, "to": { "x": 300, "y": 40 } }
  ]
}
```

Позиция узла внутри группы — относительно группы. Группа — фрейм, как в Miro: на холсте она
не сворачивается, иначе поехали бы размеры и позиции соседей, — группой объект делает только
`expand`, и объект из `expand` остаётся рамкой, даже пока жильцов нет. `refs` — ссылки на объекты, которые вьюха сама не выбирает: удалить ссылку не
значит удалить объект. `copies` — копии-отображения: тот же объект ещё раз на этом холсте, со
своим `id` — адресом и номером после `#`, своей позицией и размером, но без папки и метрик.
Копия, брошенная на фрейм, несёт его в `parent` и ездит с ним, но жильцом не становится; копию
фрейма не делают. `ends` привязывает конец связи к копии: такая стрелка идёт к ней, остальные —
к объекту, как раньше. Убранная копия уносит привязанные к ней связи, удалённый объект — свои
копии. `shapes` — фигуры, пометки на холсте без папки и метрик: `rect`, `ellipse`, `text` и `line`.
У фигуры есть `width` и `height`, заливка `color`, обводка `stroke`, `textColor`, `fontSize` и
выравнивание текста `align`. Фигура, нарисованная на группе, несёт её адрес в `parent`: `x` и `y`
у неё от группы, и с группой она ездит, копируется и удаляется. У
линии два конца, `from` и `to`, — точка `{ x, y }` или `{ node }`, узел или другая фигура, за
которыми конец едет; `arrow` — `none`, `end` или `both`. Линия — пометка, а не связь: связь
ставится стрелкой из палитры и заводит объект. Пишется файл
операциями правки, а не руками: холст и агент через [MCP](mcp.md) зовут одни и те же методы
плагина — `edit`, `undo`, `redo`.

Свёртку, стрелки и вид считает плагин (метод `view`), холст получает готовую картинку. Стрелка к
жильцу свёрнутой группы поднимается к самой группе, как в C4; несколько стрелок на одну пару
узлов склеиваются в одну с числом и списком связей; стрелка, у которой конец не попал на холст,
не рисуется.

Следит вьюха за картой сама: любое изменение карты или её `map-state.json` пересчитывает её,
пока холст на экране. Вьюха и план операции холста — код самого плагина (`model/` рядом с
`view.tsx`); саму карту операция правит через платформу (`ctx.editMap`), а свой `map-state.json`
переписывает по её ответу. Сам холст — компоненты плагина (`canvas/` рядом с `view.tsx`, на `@xyflow/react`, которую
mapward ставит в папку плагина при установке): клиент карты про холст не знает, а узлы с полным
превью холст рисует `ObjectCard` из `@mapward/component`.

## Формы данных

Кирпич `Display` плагина `views` (`_plugins/views/bricks/display.tsx`) рисует данные по виду;
пришло не то — в клетке ошибка формы, а карта работает дальше. Готовые виды отдают ему свои
данные, свой компонент берёт его относительным импортом так же.

| Вид | Форма |
| --- | --- |
| `text` | `{ text }` |
| `markdown` | `{ text }`, где текст — разметка |
| `link` | `{ label?, link? }` |
| `status` | `{ ok, summary? }` |
| `list` | `{ items: ListNode[] }` |
| `tree` | `{ children: TreeNode[] }` |
| `object` | `{ object, group?, width?, maxHeight? }` — [карточка объекта](#карточка-объекта) |

Голый массив у `list` и `tree` и голая строка у `text` и `markdown` готовые виды принимают как ту
же форму: так отвечают скрипты.

У элемента списка и дерева кроме `label` и `link` есть `status` — `fail`, `success`,
`pending`, `idle` со своими цветами, плюс свой `color` и подпись `hint` в тултипе, и `git` —
пометка файла. У элемента списка есть ещё `description` — вторая строка, приглушённая: проверке
мало сказать, что что-то не так, надо сказать, в чём именно. `action` и `actions` — кнопка и меню
строки, см. [экшоны](actions.md#где-кнопки).

`markdown` берёт ту же форму, что `text`: чтобы показать вывод по-человечески, метрике
достаточно поменять вид, не трогая источник. Разбирается подмножество, названное списком:
заголовки, абзацы, списки с вложенностью по отступу, цитаты, блоки кода, черта, а в строке —
`код`, `[ссылка](куда)`, `**жирный**` и `*курсив*`. Таблиц, картинок и html нет. Тем же
разбором, но без блоков, рисуется `description` у элемента списка и узла дерева.

`link` — адрес карты, и по схеме понятно, как его открыть: `mapward://` ведёт на объект
карты, `https://` наружу, остальное — файл в проекте. Объект карточкой, а не ссылкой, рисуется
полем `object` — ниже.

Пустой результат — это ответ, а не отсутствие ответа: у вида есть `empty` — что сказать, когда
показывать нечего. «Не проверялось» у ручной проверки, «всё сделано» у пустой очереди.

`collapsed` в `params` вида сворачивает метрику по умолчанию. Свёрнутость, переключённая руками,
живёт, пока жив вид метрики, и умолчание перекрывает: это удобство человека, репозиторию оно не
видно.

### Карточка объекта

Превью объекта там, где он встречается на чужом экране: имя с прототипом (клик открывает
объект, ctrl + клик — табом), кнопки терминала, экшонов и директив этого объекта и метрики его
вкладки превью. Своего описания у превью нет — это одна из [вкладок](index-format.md#превью-объекта)
объекта, та, у которой `defaultPreview`, или названная явно.

Отдельного вида под списки карточек нет. Карточку рисует пункт с полем `object`:

```json
{ "object": "mapward://packages/core", "group": "превью", "width": 280, "maxHeight": "240px" }
```

- у `list` и `tree` такой пункт встаёт карточкой вместо строки; `label`, `link`, статус и экшон
  строки у него не рисуются — имя, ссылка и экшоны у карточки свои. Дети узла дерева
  раскрываются под карточкой, строки и карточки в одном списке смешиваются;
- у `map` узел рисуется так, как решил конфиг вьюхи: с видом `preview` — карточкой, с `simple` —
  фигурой с подписью, а карточка открывается по клику;
- `Display` с видом `object` — одиночный объект: значение — тот же пункт. Свой компонент так
  ставит в клетку сетки карточку объекта, и метрика наследуется от прототипа, как любая.

`group` не назван — берётся вкладка с `defaultPreview`, нет и её — у карточки одна шапка.
Названной вкладки у объекта нет — карточка так и говорит, «нет вкладки …», а не подставляет
другую: чужие метрики под видом заказанных хуже пустого места. Объекта по адресу нет — «нет
объекта …».

Размер — свойство места, где карточка нарисована, а не объекта: `width` и `maxHeight`, как в
раскладках — css-строка, число значит пиксели. Без `maxHeight` карточка растёт по содержимому,
с ним шапка стоит, а метрики под ней прокручиваются целиком. Ширины нет — в списке и дереве
карточка во всю ширину, в клетке сетки — во всю клетку, на карте — ширина по умолчанию, чтобы
узлы не наезжали друг на друга.

Карточка подписана на метрики своей вкладки, пока её видно: ушла с экрана — подписка гаснет
вместе с вложенными в неё карточками. На карте детей холст рисует только видимые узлы, поэтому
цена карты — то, что на экране. Вложенность не ограничена: внутри карточки снова бывают
карточки, и круг из ссылок на себя — ответственность карты, а не инструмента.

## Свой компонент

Когда готового вида мало, метрика — свой `.tsx` рядом с `config.json`. С платформой он говорит
через `@mapward/component` — API окна: плагины хуками `usePlugin`, `useStream`, `useQuery`,
`useMutation`, ссылки — `useNavigation`, настройки смотрящего — `useViewState`, экшоны —
`useAction`, карточка объекта — `ObjectCard`. Рисует — как хочет, или из готовых кирпичей
встроенного плагина `views`: `List`, `FileTree`, `Link`, `Markdown`, `StatusDot`, `Display`,
`Grid`, `ActionButton` — исходники в `_plugins/views/bricks/`, берутся относительным импортом.

```tsx
import type { MetricProps } from "@mapward/component";
import { useNavigation, usePlugin, useStream } from "@mapward/component";
import type shell from "../../_plugins/shell/index.ts";
import { List } from "../../_plugins/views/bricks/list.tsx";

export default function Decisions({ params }: MetricProps<{ command: string }>) {
  const plugin = usePlugin<typeof shell>("../../_plugins/shell");
  const answer = useStream(["shell.json", params.command], () =>
    plugin.json({ command: params.command }),
  );
  const navigate = useNavigation();
  const items = (answer.last as { items?: [] } | undefined)?.items;
  if (!items) return <div>загружается…</div>;
  return <List items={items} onClick={navigate} />;
}
```

Рамки у своего компонента нет: подпись, время и «загружается» он рисует сам. Пропсы, хуки и
кирпичи — в [плагинах](plugins.md#метрика-компонент).

Экшон — `useAction(ключ или адрес, inputs?)`: `{ run(inputs?), running, label, description,
missing }`. `run` запускает тем же путём, что кнопка в шапке объекта, — форма, если нужна,
вопрос-подтверждение, история прогонов; `running` — сколько прогонов идёт; `missing` — экшона
нет, а пока объект-владелец экшона по адресу не пришёл — `false`: «ещё не знаем», а не «нет».

Остальное импортируется как обычно: свои файлы по относительному пути, пакеты — из
`node_modules`. Пакет ищется от папки компонента вверх до первого `node_modules`, где он есть, а
не нашёлся — в `node_modules` корня проекта. `react` и `@mapward/component` отдаёт карта, в сборку
они не кладутся: две копии React на странице ломают хуки. Собирает всё это сервер карты, esbuild
в WebAssembly, так что ставить в проект сборщик не нужно. Правка компонента или любого его файла
вне `node_modules` пересобирает его сразу.

Сборка одна на файл компонента, сколько бы метрик на него ни ссылалось, и она помнится: в памяти
сервера и на диске карты, в `.mapward/builds/`. Вместе со сборкой помнятся её входы — все ответы
файлов сборщику: прочитанное, промахи (так ищутся расширения и `index`) и пакеты в
`node_modules`. Вернулись к метрике или открыли окно — прежняя сборка показывается сразу, а
сервер сверяет входы: те же — сборка та же, иначе пересобирает и присылает новую. Обновлённый
пакет, новый файл, который сборщик нашёл бы раньше, другой сборщик (tailwind, то, что отдаёт
карта) — сборка заново. Если
компонент всё же показывает старое — `clear_build_cache` в MCP стирает сохранённое. Не собралось — в ячейке ошибки с файлом и строкой.
Упал при отрисовке — красная строка в ячейке, соседние метрики живут.

Классы — tailwind, любые, включая произвольные значения: `grid-cols-[2fr_1fr]`. Css пишется
на классы, найденные в файлах компонента, без сброса стилей, в тех же слоях, что у карты. Цвета
берутся у темы редактора, как у всей карты: `text-[var(--mw-foreground)]`,
`bg-[var(--mw-editor-background)]`. Своей темы у компонента нет.

Css компонента действует только на его территории: в его клетке и в его слое всплывающих окон.
Карта вокруг и куски карты, которые компонент вставил в себя (`ObjectCard`), его классов не
видят — одинаковый `p-2` компонента не перебивает `pl-6` карты. Меню и подсказки поверх карты
рисуются порталом в слой `useFloatingLayer()()`; вынесенное прямо в `document.body` остаётся без
классов компонента.

Типы — пакетом `@mapward/component`: его ставят в проект dev-зависимостью вместе с
`@types/react`. Работает ли компонент вместе с плагином, проверяет `mapward plugin check`: он
собирает компоненты метрик, которые ссылаются на плагин, и зовёт их запросы для агента.

## Прогоны

Прогоны метрик в историю не пишутся: история — у [экшонов](actions.md), за которой стоит
платформа. У метрики остаётся её значение, а у ответа агента — время в файле `cache`.
